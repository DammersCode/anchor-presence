The geometry scheduler is the one place where Anchor Presence touches layout. It measures each active anchor at most once per frame, and it stops all work while no remote cursor is active.

## Geometry scheduler model

One shared scheduler runs per client. There are no per-cursor measurement loops.

The scheduler exposes one method: `invalidate(reason?: string)`. Any signal calls it. The scheduler combines every call inside a frame into one `requestAnimationFrame` pass. The pass has three phases:

```text
READ PHASE     measure every active anchor once (getBoundingClientRect), plus viewport size
COMPUTE PHASE  resolve every remote cursor from the cached rects
NOTIFY PHASE   publish one immutable snapshot to subscribers
```

An active anchor is an anchor that a current remote cursor uses: the first anchor in its fallback chain that resolves. The scheduler measures each element at most once per frame. All reads happen before any consumer code runs, so one pass causes at most one forced reflow.

## Invalidation signals

The scheduler listens for these signals while at least one remote cursor is active:

- `resize` on `window`
- `scroll` on `window` and on scrollable ancestors, through one capture-phase document scroll listener
- `ResizeObserver` on each active anchor element and on `document.documentElement`
- one `MutationObserver` on `document.body` (`childList`, `attributes`, `subtree`), for moves with no dedicated signal: sibling insertion or removal, instant class toggles, transform changes
- a capture-phase scroll listener and a `MutationObserver` on each open shadow root that holds an active anchor. Document-level scroll and mutation signals stop at shadow boundaries.
- anchor register or unregister
- new remote presence data
- CSS transition and animation start and end events
- the public `invalidate()` call, for application-triggered layout changes

`ResizeObserver` alone cannot detect an element that moves without resizing. The scroll, resize, mutation and transition signals together keep [invariant 7](/docs/get-started/concepts/how-it-works#the-10-invariants): a local layout change moves a stationary remote cursor without a new network message.

### When to call invalidate() yourself

The built-in signals cover ordinary DOM mutation, resize, scroll, and animation. Some programmatic layout changes are invisible to them, for example a canvas-driven layout shift. After such a change, call `binding.invalidate()`. See [invalidate](/docs/dom/binding#invalidate) for the rules.

## Idle behavior

While no remote cursor is active, no `requestAnimationFrame` loop runs. Every scheduler signal disconnects: transition listeners, mutation observers, scroll and resize listeners, and every `ResizeObserver`. The scheduler reacts to events and never polls. When a remote cursor becomes active again, the scheduler attaches its signals again.

## Cost per frame and per message

- The scheduler runs at most one `requestAnimationFrame` pass per frame, and zero passes while idle.
- The scheduler measures each active anchor at most once per frame.
- A client publishes at 20 Hz by default (`publishIntervalMs: 50`). You can change this value per client.
- The client sends a changed `context` or `user` field once. Later cursor messages leave out the fields that did not change. Reconnect and heartbeat messages carry the current values.
- The optional `adaptivePublish` client option slows the publish rate when a transport reports a growing send buffer.
- Minified and gzipped, `@anchor-presence/core` is about 8.4 KB, `@anchor-presence/dom` about 7.6 KB, and `@anchor-presence/react` about 2.8 KB. Each size excludes React and the other Anchor Presence packages.

## Scaling limits

A room-broadcast relay forwards every message to every other socket in a room. Relay traffic therefore grows with senders times receivers. The library lowers the cost of each message: delta `context` and `user` fields, one validation pass, and an optional adaptive publish rate. It does not change the number of copies that the relay sends for each message.

For a large room, use one or more of these measures:

- Move receivers into smaller rooms.
- Add relay-side rate limits and message size caps.
- Add a server-side aggregator.

The reference relay (`apps/server`) has these limits and checks:

- a socket cap per room (`RELAY_MAX_ROOM_SOCKETS`, default 64) and per server (`RELAY_MAX_TOTAL_SOCKETS`, default 10,000)
- a byte cap per message (`MAX_MESSAGE_BYTES`, default 32 KiB). Bun closes a connection with a frame above `maxPayloadLength`: four times the cap, or at least 1 MiB.
- a token-bucket rate limit per socket (`RATE_CAPACITY`, default 80, and `RATE_REFILL_PER_SECOND`, default 40)
- an origin check and an optional [room token](/docs/dom/websocket-transport#room-token) check
- a liveness ping

The relay sends each message to its room through the topic pub-sub of Bun. One publish call reaches every other socket in the room.

Horizontal scale and authentication of identity are server concerns, not transport concerns. See [Transports](/docs/core/transports) for the boundary.

## Guidance

**Register stable anchors.** Map an anchor ID to one long-lived semantic location: a button, a row template, a section. Do not generate a new anchor ID per render for the same logical element. Each new ID adds a registry entry and forces a new registration.

**Do not register thousands of short-lived anchors.** A long list with one anchor per row grows the registry and the `MutationObserver` work with each row. Register anchors on visible or windowed rows only. For off-screen rows, use a coarser anchor, such as the list container.

**Do not call `invalidate()` on every render.** Call it only after a programmatic layout change that the built-in signals cannot see. The scheduler already combines all signals into one pass per frame. An extra call only sets a dirty flag, so it is cheap but not necessary.

## Capacity planning

A cursor message with 4 anchors is 292 bytes with `jsonCodec` and 144 bytes with `binaryCodec`. That message has two-letter anchor IDs, coordinates with one decimal place, and a small `user`. Real pointer coordinates have more decimal places, so a JSON message is larger. Measure your own messages before you plan with these numbers.

While the pointer moves, a client publishes at most once every `publishIntervalMs` (`DEFAULT_PUBLISH_INTERVAL_MS`, 50 ms). That is up to 20 messages per second per moving client. A stationary pointer sends no cursor messages. The one exception is a heartbeat every `heartbeatIntervalMs` (`DEFAULT_HEARTBEAT_INTERVAL_MS`, 10 seconds). The heartbeat carries every field, so a client that joins late gets the current values.

**Worked example.** A room has 50 clients on `binaryCodec`. 10 of them move their pointer at the same time:

- Each client receives from the 10 movers: 10 × 20 messages/s × 144 bytes ≈ 29 KB/s.
- The relay forwards every message to every other client in the room. Its outbound traffic is 10 senders × 49 receivers × 20 messages/s × 144 bytes ≈ 1.4 MB/s.

Before you commit to a capacity plan, calculate both numbers again for your own anchor count, codec, and room size.

These changes lower the load of a room:

- For a smaller wire size, pick `binaryCodec` instead of the default `jsonCodec`. See [Codecs](/docs/core/codecs).
- Split a large room into smaller rooms. A room of half the size has about a quarter of the outbound traffic.
- If a room holds more than 64 clients, raise `maxRemoteClients` above its default of 64. See [Remote presence](/docs/core/remote-presence).
- Set relay-side limits: connection quotas, message size caps, and rate limits. See [Security](/docs/get-started/guides/security).

## Measured at scale

These numbers come from two local benchmarks: a Chromium receiver test and a relay load test.

**Machine:** 13th Gen Intel Core i7-13850HX, 28 logical cores, Windows 11 Pro (build 26200), Bun 1.3.14, Playwright 1.62.1 with its bundled Chromium.

### Receiver resolve cost

A benchmark page drives N synthetic remote cursors over M registered anchors. It measures the duration of the scheduler's resolve pass on the main thread:

| Anchors × cursors | Mean pass (ms) | p95 pass (ms) |
| ----------------- | -------------- | ------------- |
| 500 × 100         | 1.72           | 2.50          |
| 1000 × 200        | 2.24           | 3.00          |
| 2000 × 200        | 2.52           | 3.30          |

### Relay load

The load test starts the reference relay. It opens N native WebSocket clients in one room. Each client publishes a real `binaryCodec` cursor message at 20 Hz.

The test measures delivery against the rate that the clients sent, not against the nominal 20 Hz. On a busy machine, timers can run below the nominal rate, so this comparison is fair. The test also measures latency percentiles and the CPU and memory of the relay process.

The 100 and 200 rows show the limit of this test setup, not a limit of the relay. All clients run in one load-generator process on the same machine. At 100 clients, that process also uses a full CPU core. The slow-receiver and rate-limit protections of the relay did not trigger: every socket stayed open, and messages queued.

| Clients | Sent (msg/s) | Delivered (msg/s) | Delivery ratio | Latency p50 | Latency p99 | Relay CPU | Relay RSS |
| ------- | ------------ | ----------------- | -------------- | ----------- | ----------- | --------- | --------- |
| 50      | 813          | 39,813            | 100%           | 16 ms       | 32 ms       | 50%       | 66 MB     |
| 100     | 1,963        | 80,408            | 41%            | 3.7 s       | 5.2 s       | 100%      | 70 MB     |
| 200     | 3,950        | 27,656            | 3.5%           | 4.0 s       | 9.4 s       | 98%       | 70 MB     |

The test raised the room and server socket caps, so the relay accepted every client under test. The rate limit stayed at the default: a burst of 40 messages, with a refill of 20 messages/s per socket.

### What this means for capacity planning

At 50 clients in one room, the reference relay delivers every message. Its p99 latency stays under 200 ms, and it uses less than one CPU core. At 100 moving clients, the relay needs about 200,000 deliveries per second. Plan rooms of up to about 50 active clients per relay process. Before you allow larger rooms, measure your own relay on your own hardware.
