description: Common problems and their causes.

Most cursor problems come from a missing anchor, a connection that is not open, or a layout change that the binding cannot see. Find your symptom below for its causes and the fix.

## Cursor not visible

Three separate causes produce the same symptom.

**The anchor is not registered.** The sender's cursor can sit over an element with no matching anchor ID on the receiver. If the fallback chain and the viewport position both miss, the resolution tier is `hidden`. Make sure that sender and receiver render the same non-empty anchor attribute value for the same semantic location.

**A visibility policy hides it.** A custom `VisibilityPolicy` can return `"hide"` for a tier that otherwise shows. Check the policy in `bindingOptions.resolution.visibilityPolicy` or `DomBindingOptions.resolution.visibilityPolicy`. The default policy hides only the `hidden` tier. Anything else that hides an `anchor` or `viewport` tier cursor is application logic. See [UI context](/docs/get-started/concepts/ui-context).

**The presence is idle or stale.** A peer (another client in the same room) is idle when its presence did not change for `idleAfterMs` (default 15000 ms). A heartbeat that changes nothing does not end idle. `CursorLayer` dims the cursor of an idle peer. The store clamps `idleAfterMs` below `staleTimeoutMs`.

The store removes a client after `staleTimeoutMs` (default 70000 ms) with no message. A sender on a background tab still sends a heartbeat every `heartbeatMs` (default 10000 ms). A browser can slow the timers of a hidden tab to one run per minute, so a long background period can still expire the entry. Make sure that the sender tab is not fully suspended, and that the transport is connected on both sides.

## Cursor is outside the window

The resolver also resolves anchors that are scrolled out of view or clipped. `ResolvedCursor.x` and `ResolvedCursor.y` are viewport pixels. To show an edge hint, compare them with the window size:

```ts
const offscreen = x < 0 || y < 0 || x > window.innerWidth || y > window.innerHeight;
```

See [Off-screen hints](/docs/get-started/guides/offscreen-hints) for a full recipe.

## Cursor floats over empty space

An anchor can be measurable while an internal scroll container clips it. The resolver sets `pointVisible` to false when the resolved point is outside the clipped area. The default policy still shows the cursor. See [Occlusion and scroll](/docs/dom/occlusion-and-scroll) for a policy that hides these cursors, and for the limits of the check.

## Cursor drifts

A resolved cursor can slowly move away from its target element. The cause is a moving container that the automatic invalidation signals of the scheduler do not cover.

The built-in signals cover `resize`, `scroll`, `ResizeObserver`, a `MutationObserver` on `document.body`, and CSS transition and animation events. Some layout changes are outside all of these signals. One example is a manual `style.transform` write in a `requestAnimationFrame` loop with no CSS transition. Such a change does not start a new measurement.

After a programmatic layout change that the built-in signals do not cover, call the binding's `invalidate()`:

```ts
binding.invalidate("custom-layout-change");
```

See [Invalidation signals](/docs/get-started/guides/performance#invalidation-signals) for the full signal list.

## Cursor jumps between two elements

If the pointer crosses a gap with no anchored parent, the fallback chain drops to the viewport position. The viewport position maps to a different spot in a receiver layout that arranges elements differently, so the cursor jumps.

Give the parent container its own anchor, for example `data-anchor="nav"` on a sidebar. A pointer that crosses the gap between two child anchors then resolves against the shared parent, not against the viewport. The live demo uses `data-anchor="nav"` on its sidebar for this reason.

A jump can also occur with no gap: two neighbors in one layout can sit far apart in the other layout. For layout rules that prevent both cases, and a skill that measures them, see [Layout design for presence](/docs/get-started/guides/layout-design).

## Plain HTTP

`createPresenceClient` generates a `clientId` and a `session` value with an `idFactory`. The default factory builds a 12-character ID from 72 random bits of `crypto.getRandomValues()`, which works on plain HTTP too. When `crypto` is missing, it uses a mix of `Date.now()` and `Math.random()`.

For this reason, client creation never throws on plain HTTP. For a specific ID format or an externally issued ID, pass your own `idFactory` or a fixed `clientId` through `PresenceClientOptions`.

## Two tabs share one clientId

A `clientId` identifies a client instance, not a user. Two live tabs that share one `clientId` generate two different `session` values, because `session` is random per client instance.

The sequence rule of the receiver treats a session change as a restart. It accepts the messages of the new session and resets the stored sequence number. Two tabs that share a `clientId` look like a restart on every message. The visible cursor then jumps between the positions of the two tabs.

The library does not report this error. Give every tab or connection its own `clientId`. Attach the user identity through the `user` field, and do not reuse a `clientId` across tabs.

## Tests in jsdom

jsdom has no real layout. `getBoundingClientRect()` always returns zeros unless a test mocks it. `ResizeObserver` and `MutationObserver` can be absent, or behave differently from a real browser.

A unit test in jsdom can check the logic of your own code with mocked rects. Cross-layout behavior needs a real-browser test, for example with Playwright on Chromium, Firefox, and WebKit. Examples of cross-layout behavior are wrapping, sidebar states, and element-size proportions.

If a behavior looks correct in a jsdom test but wrong in the browser, suspect a jsdom gap first. Make sure that the real browser has the observer or CSS feature that the test mocked.
