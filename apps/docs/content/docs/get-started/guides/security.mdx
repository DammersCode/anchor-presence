Every inbound message comes from a peer, so treat it as untrusted. This page lists what the library protects, and what your app and your relay must protect. Read it before you put Anchor Presence in production.

## The short version

- The client drops messages and fields above the validation limits.
- Anchor IDs never reach a selector or code.
- Your app renders `user` and `context` as text.
- Your server, not the protocol, proves who a peer is.

## Validation limits

The client checks each inbound message in two steps:

1. It drops a message above `maxMessageBytes` (32 KiB) before it decodes the message.
2. It passes the decoded message to `validatePresence()`.

`validatePresence()` drops a message with an invalid `version`, `clientId`, `session`, `sequence`, or `cursor` shape. If only `user` or `context` breaks a limit, it drops that field and keeps the rest of the message. It clamps `u` and `v` to the range 0 to 1. [ValidationLimits](/docs/core/validation#validationlimits) lists every limit, its default, and the result of a break. The validation defaults are the `DEFAULT_MAX_*` constants of `@anchor-presence/core`. To change a limit, pass `validationLimits` to `createPresenceClient`.

<Callout type="warn">
  If your relay calls `validatePresence`, cap the frame size on the relay. `validatePresence` ignores
  `maxMessageBytes`, because a decoded message has no byte length. See [Relay
  contract](/docs/examples/backends/relay-contract).
</Callout>

Each receiver also limits the rate of inbound events with the `eventRateLimit` option. See [Event rate limit](/docs/core/events#event-rate-limit). This limit protects one receiver only. A sender can still flood the room, so the [rate limit per socket](/docs/get-started/guides/deploy-relay#set-the-environment-variables) on the relay is the real control.

## Why anchor IDs never touch selectors

An anchor ID is an opaque string. The resolver looks it up as a key in a `Map<string, Element>`. The library never passes it to `querySelector`, `eval`, a template engine, or any code that reads a string as a program.

As a result, an anchor ID from the network can only address an element that your app registered. An unknown ID is a lookup miss, and the fallback chain handles it as a normal case.

## Render user and context as text

Validation checks the size of `user` and `context`, not the content. A peer can put any string into them. Render both as text: a text node in DOM code, or `{value}` in JSX.

<Callout type="warn">
  If you render `user` or `context` as HTML, through `innerHTML`, `dangerouslySetInnerHTML`, or an equivalent,
  a peer can inject markup and scripts into your page.
</Callout>

This sample shows the correct and the wrong way to render a remote name:

```tsx
import type { ResolvedCursor } from "@anchor-presence/react";

function RemoteName({ cursor }: { cursor: ResolvedCursor<unknown, { name: string }> }) {
  return (
    <>
      {/* correct: renders as text, no matter what the string contains */}
      <span>{cursor.user?.name}</span>
      {/* wrong: never do this with network-sourced data */}
      <span dangerouslySetInnerHTML={{ __html: cursor.user?.name ?? "" }} />
    </>
  );
}
```

## Check the shape of remote values

A peer can send `{ name: {} }` where you expect a string. React throws when it renders that object as a child.

If you pass a local `user` or `context` to `createPresenceClient`, the client compares each remote value with its shape. For example, with `user: { name: "Ada" }`, a remote `user` must be an object whose `name` is a string, `null`, or missing. The client drops a value that does not fit, and keeps the previous value. Your render code must accept `null` and missing fields. [Remote user and context](/docs/core/validation#remote-user-and-context) lists every rule.

A client with no local value has no shape to compare with. Pass `parseUser` or `parseContext` instead. Return `undefined` to drop the value:

```ts
const client = createPresenceClient<unknown, { name: string; avatar?: string }>({
  transport,
  parseUser: (value) => {
    const { name, avatar } = value as { name?: unknown; avatar?: unknown };
    if (typeof name !== "string") return undefined;
    const safeAvatar = typeof avatar === "string" && avatar.startsWith("https://") ? avatar : undefined;
    return safeAvatar === undefined ? { name } : { name, avatar: safeAvatar };
  },
});
```

Check every URL and CSS value from a peer before you use it. A peer can send a `javascript:` URL, or a string that breaks out of a CSS value. Allow only `https://` URLs. Allow only colors that match a fixed pattern, such as `/^#[0-9a-f]{6}$/i`, or that are in a list you own.

In development mode, the client warns when no check applies to a remote value, and when the shape check drops a value.

## Identity is not authenticated

`clientId` and `session` are plain fields on the wire. Any peer can send any value. The store accepts a new session for a known `clientId` with no proof that the same person sent both.

If your app must know who sent a message, bind the identity on your server. The [relay contract](/docs/examples/backends/relay-contract#identity) shows how a relay replaces `clientId` and `user` with a verified identity.

## maxRemoteClients

`maxRemoteClients` caps the store entries, resolved cursors, and observed anchors that network data causes. The default is on [Remote presence](/docs/core/remote-presence#maxremoteclients). The [event rate limit](/docs/core/events#event-rate-limit) has a separate cap: it tracks at most 512 senders.

A peer can fill every slot with new `clientId` values. Real clients then stay out until those entries expire after `staleTimeoutMs`. Set `maxRemoteClients` to the number of sessions that you expect at the same time.

## Room token

A **room token** is a secret that the relay checks before it accepts a connection. If `RELAY_AUTH_TOKEN` is set, the reference relay requires a matching [room token](/docs/dom/websocket-transport#room-token). It closes a connection with a missing or wrong token with code `4006`.

- To limit who can connect by origin, set `RELAY_ALLOWED_ORIGINS`. The relay closes a connection from another origin with code `4004`. See [Set the environment variables](/docs/get-started/guides/deploy-relay#set-the-environment-variables).
- The room token controls who can connect. It does not prove the identity inside a message.
- The reference relay and the example relays compare all connections with one `RELAY_AUTH_TOKEN`, so one token opens every room.
- To limit a token to one room, check the `room` field in your own [`authCheck` hook](/docs/examples/backends/relay-contract#identity).
- The transport sends the token in the `token` query parameter. Proxies and servers often write the full URL into their access logs.

<Callout type="warn">
  If you use a long-lived room token, anyone who reads the access logs can join the relay. Create a
  short-lived token for each session on your server, and check it in your own `authCheck`. On the client, pass
  a `token` function to `createWebSocketTransport`. The transport calls it before each connection attempt.
</Callout>
