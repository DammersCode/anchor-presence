`validatePresence` turns an untrusted decoded value into a `PresenceMessage` or `null`. The client passes the output of every codec `decode` through it before the value reaches the store. Call it yourself only when you process presence data outside a `PresenceClient`, for example on a relay.

## Use validatePresence directly

This relay function drops an oversized frame first, then checks the decoded value:

```ts
import { DEFAULT_MAX_MESSAGE_BYTES, jsonCodec, validatePresence } from "@anchor-presence/core";

function inspect(frame: Uint8Array) {
  if (frame.byteLength > DEFAULT_MAX_MESSAGE_BYTES) return null;
  return validatePresence(jsonCodec.decode(frame));
}
```

`inspect` returns a well-formed `PresenceMessage`, or `null` for a message to drop. `validatePresence` never throws. The `user` and `context` of the result have the type `unknown`. It clamps anchor and viewport coordinates into the range `0` to `1`.

<Callout type="warn">
  If a relay calls `validatePresence`, cap the frame size before the decode. `validatePresence` ignores
  `maxMessageBytes` and accepts an oversized message.
</Callout>

## The validation boundary

The client runs these steps on each inbound message, in this order:

<div role="region" aria-label="Incoming message checks diagram" tabIndex={0} className="overflow-x-auto">
  <Mermaid
    chart={`flowchart TD
  accTitle: Incoming message checks
  bytes["bytes"] --> checks["steps 1 to 4"]
  checks -->|fails| drop["drop"]
  checks -->|steps 5 and 6| listeners["event listeners"]
  checks -->|steps 7 and 8| store["store"]`}
  />
</div>

1. The client drops the message when its byte length is more than `maxMessageBytes`.
2. It decodes the bytes with the codec.
3. It calls `validatePresence` on the decoded value. A `null` result drops the message. The result is `null` in these cases:
   - `version` is not `1`.
   - `clientId` is not a string of 1 to `maxClientIdLength` characters.
   - `session` is not a string of 1 to `maxSessionLength` characters.
   - `sequence` is not an integer from `0` to `maxSequence`.
   - `cursor` is neither `null` nor an object.
   - `cursor.anchors` is not an array.
4. It drops an echo of its own message.
5. It applies the [event rate limit](/docs/core/events#event-rate-limit) to an event message. A message over the limit is dropped.
6. It passes an event message that stays to `parseEvent`, when you set one, and then to the event listeners. An event message stops at this step.
7. It checks `user` and `context` with `parseUser` and `parseContext`, or with the shape check when no parser is set.
8. It gives the message to the store.

A codec does not check limits. Its job is to turn bytes into a value and back, without a throw. `validatePresence` checks the decoded value against the protocol limits.

## ValidationLimits

`ValidationLimits` overrides one or more default limits. Omit a field to keep its default. Each default is an exported `DEFAULT_` constant with the same name in upper case, for example `DEFAULT_MAX_ANCHORS`.

| Field               | Default      | Limit                                                    | Result when a message breaks the limit                       |
| ------------------- | ------------ | -------------------------------------------------------- | ------------------------------------------------------------ |
| `maxClientIdLength` | `128`        | Length of `clientId`                                     | Drops the message.                                           |
| `maxSessionLength`  | `64`         | Length of `session`                                      | Drops the message.                                           |
| `maxSequence`       | `2147483647` | Largest `sequence`. A `sequence` is an integer from `0`. | Drops the message.                                           |
| `maxAnchors`        | `8`          | Number of anchors in one cursor                          | Keeps the first `maxAnchors` anchors.                        |
| `maxAnchorIdLength` | `256`        | Length of an anchor `id`                                 | Drops that anchor only.                                      |
| `maxFieldBytes`     | `8192`       | JSON size in bytes of `user`, `context`, or event `data` | Drops the `user` or `context` field. Drops an event message. |
| `maxFieldDepth`     | `8`          | Nesting depth of `user`, `context`, or event `data`      | Drops the `user` or `context` field. Drops an event message. |
| `maxMessageBytes`   | `32768`      | Byte length of one encoded message                       | The client drops the message. `validatePresence` ignores it. |

The `maxAnchors` cut comes before the anchor checks. An invalid anchor among the first `maxAnchors` anchors leaves a shorter chain.

`validatePresence` also checks `pointer`. It keeps a `pointer` with the `type` `mouse`, `pen`, or `touch`, or with no `type`. It drops a `pointer` with any other `type` and keeps the rest of the message.

Pass the limits as the second argument of `validatePresence`, or through `validationLimits` on `createPresenceClient`:

```ts
const client = createPresenceClient({
  transport: myTransport,
  validationLimits: { maxAnchors: 4 },
});
```

See [Security](/docs/get-started/guides/security) for the risk that each limit covers.

## Remote user and context

`validatePresence` checks the size and depth of `user` and `context`, not their shape. The client adds a shape check for each remote value.

Without a parser, the shape check compares a remote value with the local value of the same field. A client with this local `user` accepts a remote `user` whose `name` and `color` are strings or `null`:

```ts
const client = createPresenceClient({
  transport: myTransport,
  user: { name: "Ada", color: "#e11d48" },
});
```

When a part of the remote value does not fit, the client drops the whole field. The client reads the local value for each message, so `setUser` and `setContext` change the shape.

<Accordions>
  <Accordion title="Rules of the shape check">

    - A remote `null` always fits, at every level. For example, a key with a local string value accepts a remote `null`. As a result, a key typed `T | null` stays valid.
    - A key of the local object must have the type of the local value, or be `null`. A remote object can omit a key.
    - An extra key is a key that the local object does not have. An extra key stays when its value is a string, a number, a boolean, or `null`. The check removes an extra key that holds an object or an array. This rule also applies to an empty local object.
    - The check removes a `__proto__` key at every level.
    - An array must be an array. Each item must have the shape of the first local item, or be `null`. An empty local array accepts an array of strings, numbers, booleans, or `null` values.
    - A string, a number, or a boolean must have the type of the local value, or be `null`.
    - A local `null` value, or a local `undefined` value inside an object, accepts a string, a number, a boolean, or `null`. It never accepts an object or an array.
    - If the local `user` or `context` is `undefined`, no check runs.

  </Accordion>

  </Accordions>

`parseUser` and `parseContext` replace the shape check. They also give the `user` and `context` their types. Without them, both types are `unknown`, because the shape check never types a value. The parser receives the remote value and returns the value to store. Return `undefined` or throw to drop the field:

```ts
const viewer = createPresenceClient<{ page: string }>({
  transport: myTransport,
  parseContext: (value) => {
    const { page } = value as { page?: unknown };
    return typeof page === "string" ? { page } : undefined;
  },
});
```

A dropped field does not clear the stored value. The receiver keeps the previous value of the same session. A `null` field value clears the field, and no check runs on it.

<Callout type="warn">
  If a client has no local `user` or `context`, pass `parseUser` or `parseContext`. Without a local value or a
  parser, the client accepts the remote value as it is, and a malformed value reaches your render.
</Callout>

In development mode, the client warns when a remote value arrives with no check, and when the shape check drops a value. See [Development mode](/docs/core/presence-client#development-mode). See [Security](/docs/get-started/guides/security#check-the-shape-of-remote-values) for the render risk.

## Events and leave messages

An event message has a `null` cursor and an `event` field. `validatePresence` drops the whole message in these cases:

- The event `type` is not a string of 1 to `MAX_EVENT_TYPE_LENGTH` characters.
- The event `data` breaks `maxFieldBytes` or `maxFieldDepth`.

As a result, a bad event never reaches the store as a message that clears the cursor. `validatePresence` does not check the shape of the event `data`. To check it, pass `parseEvent`. See [Events](/docs/core/events).

`validatePresence` keeps `leave: true` only on a message with a `null` cursor.
