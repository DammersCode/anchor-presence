title: UI context
description: Opaque context, visibility policies, dialog mismatch handling, and the receiver-UI rule.
---

UI context is application state, such as an open dialog, that a sender attaches to its cursor. A peer is another client in the same room. A visibility policy on the receiver reads the context of each peer to show or hide its cursor. Anchor Presence never changes the UI state of the receiver.

## Opaque context

`CursorPresence` carries an optional `context` field. `@anchor-presence/core` gives this field no meaning. It checks the size of the context, 8 KiB of JSON at most. If the client has a local context, it also checks the shape of each remote context. See [Remote user and context](/docs/core/validation#remote-user-and-context) for the shape check.

Set context on the client:

```ts
client.setContext({ route: "/settings", dialog: "invite" });
```

The client sends each change to context one time. Full publishes (reconnect and heartbeat) include the current context. A missing field means "unchanged since the previous same-session message". An explicit `null` clears it. On the receiver, context reaches two places: the visibility policy input, and the `context` field on each `ResolvedCursor`.

Use context for the state that a receiver needs to decide how to show a cursor. Examples are the route, the open dialog, and the active tab. See [Security](/docs/get-started/guides/security) for validation limits and rendering rules.

<Callout type="warn">
  If you put private data in context, every receiver in the room gets it. The client sends context on each
  change and on each full publish.
</Callout>

## Visibility policies

A visibility policy is a pure function that decides whether a resolved cursor shows:

```ts
type VisibilityPolicy<TContext = unknown, TUser = unknown> = (input: {
  presence: CursorPresence<TContext, TUser>;
  resolution: { tier: ResolutionTier; anchorId: string | null; pointVisible: boolean };
}) => "show" | "hide";
```

`ResolutionTier` is `"anchor" | "viewport" | "hidden"`.

The default policy shows cursors at the `anchor` and `viewport` tiers, and hides cursors at the `hidden` tier. See [The default policy](/docs/dom/visibility-policy#the-default-policy).

Pass a custom policy through `DomBindingOptions.resolution.visibilityPolicy` (`@anchor-presence/dom`) or `bindingOptions.resolution.visibilityPolicy` on `LiveCursorProvider` (`@anchor-presence/react`). A custom policy can read `presence.context` to apply application-specific rules on top of geometric resolution.

A policy can also read `resolution.pointVisible` to hide a cursor clipped by a scroll container. See [Occlusion and scroll](/docs/dom/occlusion-and-scroll) for how the resolver computes it and where the check falls short.

## Dialog mismatch handling

Anchor fallback covers most context mismatches. For example, the cursor of a sender sits inside the anchor `settings.dialog.invite`. That dialog is closed on the receiver, so the anchor is absent from its DOM. The fallback chain then moves to a parent anchor, for example `settings`, or to the viewport.

A cursor at the wrong place misleads the receiver. Some cases therefore need an explicit policy instead of geometric fallback. Three approaches work:

- **Hide the cursor.** If `presence.context?.dialog` names a dialog that is closed on the receiver, return `"hide"`.
- **Fall back to the dialog trigger anchor.** Register the button that opens the dialog under a stable anchor ID. When the dialog anchor is absent, the fallback chain lands on the trigger button.
- **Show a passive presence indicator.** Do not hide the cursor. Render a muted version for the `hidden` tier, with `tier` and `context` from the resolved cursor.

This policy hides the cursor of a sender whose open dialog differs from the dialog of the receiver:

```ts
const dialogAwarePolicy: VisibilityPolicy<{ dialog?: string }> = ({ presence, resolution }) => {
  const senderDialog = presence.context?.dialog;
  if (typeof senderDialog === "string" && senderDialog !== myOpenDialogId()) return "hide";
  return resolution.tier === "hidden" ? "hide" : "show";
};
```

The client must have the same context type as the policy, for example `createPresenceClient<{ dialog?: string }>`. When the open dialog of the receiver changes, call `binding.invalidate()`, so that the policy runs again. See [Run the policy again after a state change](/docs/dom/visibility-policy#run-the-policy-again-after-a-state-change).

## The "never change receiver UI state" rule

Anchor Presence never changes what the receiver's UI shows. Resolving a remote cursor position must not force a route change, open or close a dialog, expand a sidebar, or scroll the page.

This rule keeps the receiving user in full control of their own screen. A remote cursor only gives information. A resolved position can land inside UI that is closed on the receiver. Then the correct response is fallback or hide. Never force that UI open to match the sender.

Do not change local UI state, such as dialogs, routes, or sidebar toggles, as a reaction to `useRemoteCursors()` or `useRemotePresence()`. Use `context` for display decisions only.
