This page lists common problems, their causes, and the fix for each one.

## Cursor not visible

Three separate causes produce the same symptom.

**The anchor is not registered.** If the sender's cursor sits over an element with no matching anchor ID on the receiver, and the fallback chain and viewport both miss, the resolution tier is `hidden`. Make sure both sender and receiver render the same non-empty anchor attribute value for the same semantic location.

**A visibility policy hides it.** A custom `VisibilityPolicy` can return `"hide"` for a tier that otherwise shows. Check the policy passed to `bindingOptions.resolution.visibilityPolicy` or `DomBindingOptions.resolution.visibilityPolicy`. The default policy hides only the `hidden` tier. Anything else hiding an `anchor` or `viewport` tier cursor is application logic. See [UI context](/docs/get-started/concepts/ui-context).

**The presence is stale.** A remote client with no message for `idleAfterMs` (default 15000 ms) is idle: `CursorLayer` dims its cursor. The store removes the client after `staleTimeoutMs` (default 70000 ms) with no message. The client clamps `idleAfterMs` below `staleTimeoutMs`. A sender on a backgrounded tab still sends a heartbeat every `heartbeatMs` (default 10000 ms), but a browser can clamp hidden-tab timers to one minute. A very long background period can still expire the entry. Make sure the sender tab is not fully suspended, and make sure the transport is still connected on both sides.

## Cursor is outside the visible area

The resolver also resolves anchors that are scrolled out of view or clipped. `ResolvedCursor.x` and `ResolvedCursor.y` are viewport pixels. To show an edge hint, compare them with the viewport:

```ts
const offscreen = x < 0 || y < 0 || x >= window.innerWidth || y >= window.innerHeight;
```

## Cursor floats over empty space

An anchor can be measurable while an internal scroll container clips it. The resolver sets `pointVisible` to false when the resolved point is outside the clipped area. The default policy still shows the cursor. See [Occlusion and scroll](/docs/dom/occlusion-and-scroll) for a policy that hides these cursors, and for the check's limits.

## Cursor drifts

A resolved cursor that slowly separates from its target element usually means a moving container is not covered by the scheduler's automatic invalidation signals.

The built-in signals cover `resize`, `scroll`, `ResizeObserver`, a `MutationObserver` on `document.body`, and CSS transition and animation events. A layout change outside all of these, for example a manual `style.transform` write driven by a `requestAnimationFrame` loop with no matching CSS transition, does not trigger a re-measure by itself.

Call the binding's `invalidate()` after any programmatic layout change the built-in signals do not cover:

```ts
binding.invalidate("custom-layout-change");
```

See [Performance](/docs/get-started/guides/performance) for the full signal list and when to call `invalidate()` yourself.

## Cursor jumps between two elements

If the pointer crosses a gap with no anchored parent, the fallback chain drops to the viewport position. The viewport position maps to a different spot in a receiver layout that arranges elements differently, so the cursor jumps.

Give the parent container its own anchor, for example `data-anchor="nav"` on a sidebar. A pointer that crosses the gap between two child anchors still resolves against the shared parent, instead of falling back to the viewport. The live demo uses `data-anchor="nav"` on its sidebar for this reason.

A jump can also occur with no gap: two neighbors in one layout can sit far apart in the other layout. For layout rules that prevent both cases, and a skill that measures them, see [Designing layouts for presence](/docs/get-started/guides/layout-design).

## HTTP vs HTTPS

`createPresenceClient` generates a `clientId` and a `session` value using an injected `idFactory`. The default factory prefers `crypto.randomUUID()`, available only in a secure context (HTTPS, or `localhost`). On a plain HTTP origin, `crypto.randomUUID` is absent, and the default factory falls back to `crypto.getRandomValues()`, then to a `Date.now()`/`Math.random()` combination if neither is available.

This fallback chain means client creation never throws on plain HTTP. If you need a specific ID format or an externally issued ID, pass your own `idFactory` or a fixed `clientId` through `PresenceClientOptions`.

## Two tabs, same clientId, flapping

A `clientId` identifies a client instance, not a user. Two live tabs that share one `clientId` generate two different `session` values, because `session` is random per client instance.

The receiver's sequencing rule treats a session change as a restart: it accepts the new session's messages and resets the stored sequence number. With two tabs sharing a `clientId`, every message from either tab looks like a restart from the other tab's point of view, and the visible cursor flaps between the two tabs' positions.

This is not an error the library reports. It is a sign of misuse. Give every tab or connection its own `clientId`. Attach user identity through the `user` field instead of reusing `clientId` across tabs.

## jsdom vs a real browser

A unit test suite that runs in jsdom lacks real layout. `getBoundingClientRect()` always returns zeros unless a test mocks it. `ResizeObserver` and `MutationObserver` are often absent, or behave differently from a real browser.

Because of this, `@anchor-presence/dom` and `@anchor-presence/react` unit tests use injectable observer factories and mocked rects to test scheduler and resolver logic without real layout. Real cross-layout correctness needs a real-browser test suite, for example Playwright across Chromium, Firefox, and WebKit. Examples of real cross-layout correctness are wrapping, sidebar states, and element-size proportionality.

If a scheduler or resolver behavior looks correct in a jsdom unit test but wrong in the browser, suspect a jsdom API gap first. Check that the real browser has the observer or CSS feature the test mocked.
