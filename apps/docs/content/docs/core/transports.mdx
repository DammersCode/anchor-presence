A transport is the byte channel between a presence client and the network. `@anchor-presence/core` imports no transport library. You give the client an object that implements `PresenceTransport`. Read this page before you write a transport. It also explains the connection status and the close reasons.

## Use a transport

Pass a transport instance to `createPresenceClient`:

```ts
import { createPresenceClient } from "@anchor-presence/core";

const client = createPresenceClient({ transport: myTransport });
```

## The PresenceTransport interface

`@anchor-presence/core` exports `PresenceTransport`, `ConnectionStatus`, and `TransportClose` with these shapes:

```ts
interface PresenceTransport {
  connect?(): Promise<void> | void;
  disconnect?(): Promise<void> | void;
  send(data: Uint8Array): Promise<void> | void;
  subscribe(listener: (data: Uint8Array) => void): () => void;
  subscribeStatus?(listener: (status: ConnectionStatus) => void): () => void;
  subscribeClose?(listener: (close: TransportClose) => void): () => void;
  getStatus?(): ConnectionStatus;
  bufferedBytes?(): number;
}

type ConnectionStatus = "connecting" | "connected" | "reconnecting" | "disconnected";

type TransportClose = { code?: number; reason?: string; willReconnect: boolean };
```

Only `send` and `subscribe` are required:

- `send` receives encoded bytes. The client calls `codec.encode()` before it calls `send`. The client catches each throw and each rejection from `send`, because presence can lose a message and stay correct. A lost message does not stop the client.
- `subscribe` delivers encoded bytes from the wire. The client then calls `codec.decode()` and `validatePresence()` on them.

## Connect and disconnect ownership

`connect` and `disconnect` are optional. By default, the client calls `connect()` one time, during creation. With `autoConnect: false`, you call `connect()` yourself, before or after you pass the transport to `createPresenceClient`. See [Connect the transport](/docs/core/presence-client#connect-the-transport).

`client.dispose()` calls `transport.disconnect()` when the transport has one, in both modes. A throwing `disconnect` does not stop the other cleanup of `dispose`.

## Connection status

`subscribeStatus` and `getStatus` are optional. The client reads them with these rules:

- Without `subscribeStatus`, the client reports a constant `"connected"` status. It never reads `getStatus` in this case.
- With `subscribeStatus`, the client reads `getStatus()` one time, at creation, for its first status. Without `getStatus`, the client starts at `"connecting"` until the first status callback arrives.

Replay the current status to every new subscriber inside `subscribeStatus`. Without a replay, a client that subscribes after the connection opened never learns that it can send.

Every change of the status to `connected` makes the client publish its full state again. Only a change from `reconnecting` or `disconnected` also expires each peer that no message confirms. See [After a reconnect](/docs/core/remote-presence#after-a-reconnect).

`bufferedBytes` is optional. It reports the number of bytes in the send queue of the transport. The client uses it only for the `adaptivePublish` option. See [Publish rate](/docs/core/presence-client#publish-rate).

## Close reasons

`subscribeClose` is optional. A transport that implements it calls each listener each time a connection closes, with a `TransportClose`:

- `code` is the close code, for example `4006` for a rejected room token.
- `reason` is the close reason text, when the relay sent one.
- `willReconnect` is `true` when the transport schedules another attempt.

`client.subscribeClose(listener)` forwards the listener to this method. If the transport has no `subscribeClose`, the client never calls the listener. See [Custom transport](/docs/core/custom-transport#close-reasons) for a sketch.
