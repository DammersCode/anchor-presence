title: Layout audit skill
description: The agent skill that scores a running app for cursor-jump risk between layouts and proposes fixes.

The layout audit skill measures how far a remote cursor can jump when your app's layout changes: a sidebar that collapses, a table that becomes cards, a breakpoint that reflows a grid. Install it and ask your agent to audit your layouts; it drives a real browser against your running app and hands back a score, per view pair, with concrete fixes.

## What it does

The agent scans your code for anchors, routes, breakpoints, and toggles such as a collapsible sidebar or a dialog. It builds a list of views, routes crossed with viewport widths and UI states, and measures every pair of views of the same page in a real browser. Each pair gets a score from 0 (low risk) to 100 (high risk), broken into five sub-scores. For any pair that scores moderate or high, the agent proposes fixes, file and line, and applies the ones you pick.

## When to reach for it

| Situation                                                            |                             Reach for it                             |
| -------------------------------------------------------------------- | :------------------------------------------------------------------: |
| Before shipping a responsive or collapsible layout with live cursors |                                 Yes                                  |
| Remote cursors jump between two layouts                              |                                 Yes                                  |
| Reviewing a layout for live presence risk                            |                                 Yes                                  |

## What it asks you

| Question               | Options                                                                      | Default                             |
| ---------------------- | ---------------------------------------------------------------------------- | ----------------------------------- |
| URL of the running app | Any HTTP URL, or let the agent start the dev script                          | Asked; the code cannot answer this  |
| Views to measure       | Confirm, remove, or add rows in the proposed route × viewport × state matrix | The proposed matrix, once confirmed |
| Report format          | `table`, `markdown`, `mermaid`, or a comma-separated combination             | `table`                             |
| Which fixes to apply   | Pick by number from the proposals, per view pair                             | None applied until you pick         |

## How it works

1. **Scan.** The agent finds every `data-anchor` in your code, the routes that render them, your breakpoints, and toggles that change which anchors show or where they sit.
2. **Propose a matrix.** It builds views from routes, viewport widths (a base set plus your breakpoints), and states (default plus one per toggle), and shows you the pair count before measuring.
3. **Check prerequisites.** It confirms the app URL answers and that Playwright is installed.
4. **Measure.** It opens each view in a real browser, records anchor boxes, and scores every pair.
5. **Report.** It asks your preferred format and shows or writes the results.
6. **Propose fixes.** For each pair scoring moderate or high, it matches the worst sub-scores to a fix and cites the file and line.
7. **Apply and re-measure.** It applies only the fixes you pick, then measures again and shows a before/after table.

## Output formats

| Format      | Content                                                                                   | Rough chat cost                                               |
| ----------- | ----------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| `table`     | One row per view pair (top 15): total, band, five sub-scores                              | About 40 tokens per row, 600 for 15 rows                      |
| `markdown`  | A file: the score table, then per pair the inputs, largest jumps, gaps, shapes, fallbacks | About 30 tokens for the path; the script prints the file size |
| `mermaid`   | A file: bar charts of total and jump distance per pair, plus fallback-chain flowcharts    | About 30 tokens for the path                                  |
| Combination | `table,markdown`, `markdown,mermaid`, or `all`                                            | The sum of the parts; the files merge into one                |

## Score bands

Each sub-score runs from 0 to 100. It is 0 at or below the first value, 100 at or above the second, and linear in between:

| Sub-score | Weight | What it measures                                                         | 0 at        | 100 at       |
| --------- | :----: | ------------------------------------------------------------------------ | ----------- | ------------ |
| Jump      |  35%   | How far apart two neighboring anchors land in the other view (90th pct.) | 40 px       | 240 px       |
| Gap       |  25%   | Share of a container where the pointer has no anchored parent            | 5%          | 40%          |
| Depth     |  15%   | How many levels an anchor falls back in the other view                   | 0           | the viewport |
| Aspect    |  15%   | How much an anchor's width-to-height ratio changes (90th pct.)           | 1.3 × ratio | 3 × ratio    |
| Parity    |  10%   | Share of anchor IDs that exist in one view only                          | 0%          | 100%         |

The total is the weighted sum, but never lower than Jump or Gap. Users see a large jump or a large gap on its own, so the other sub-scores cannot dilute it.

| Total  | Band     |
| ------ | -------- |
| 0–20   | Low      |
| 21–50  | Moderate |
| 51–100 | High     |

See [Scoring a view pair](https://github.com/DammersCode/anchor-presence/blob/main/skills/anchor-presence-audit/scoring.md) in the skill source for the exact formula.

## Common questions

**Does it need my app in production?** No. Point it at any running instance, including `localhost`. Nothing it measures leaves your machine.

**What if I have no Playwright installed?** The skill detects this and gives you the exact install command for your package manager; it asks before installing anything.

**Can I run this in CI?** Yes. Run `measure.mjs` with `--fail-above <score>`; the script exits with code 1 when any view pair scores above that value, so a pipeline can fail the build on a regression.

**Does it fix things automatically?** No. It proposes fixes per pair and applies only the ones you pick, one round per run.

**What counts as one view?** One route, at one viewport width, in one UI state — for example, the orders page at 768 px with the sidebar collapsed.

## It's working if

- The measurement summary reports every view measured (`Measured N/N views`).
- Every pair scoring moderate or high has a proposal, or a stated reason why no fix applies.
- After applying fixes, the before/after table shows the picked pairs' totals dropping, with no pair getting worse without a note.
- A CI run with `--fail-above` exits 0 once every pair is at or below your chosen threshold.
