`useRemoteUsers` returns one entry for each peer. An entry holds the `user` value of the peer, its session, and its idle state. Use it for a presence list or an avatar stack. These lists need one row per client (tab), and they do not rerender when cursors move.

## Usage

This component lists the peers and dims the idle ones:

```tsx
import { useRemoteUsers } from "@anchor-presence/react";

type MyUser = { name: string; color: string };

function PresenceList() {
  const users = useRemoteUsers<MyUser>();
  return (
    <ul>
      {users.map((entry) => (
        <li key={entry.clientId} style={{ opacity: entry.idle ? 0.5 : 1 }}>
          {entry.user?.name ?? "Guest"}
        </li>
      ))}
    </ul>
  );
}
```

For a full presence list with avatars, see the [Presence list](/docs/examples/presence-list) example.

## RemoteUser fields

| Field      | Type                 | Meaning                                                                                     |
| ---------- | -------------------- | ------------------------------------------------------------------------------------------- |
| `clientId` | `string`             | the peer that sent the user value                                                           |
| `user`     | `TUser \| undefined` | the user value, or `undefined` when the peer sent none or sent `null`                       |
| `session`  | `string`             | the session ID of the peer                                                                  |
| `idle`     | `boolean`            | `true` when the presence of the peer did not change for `idleAfterMs`, even with heartbeats |

## User shape

The client checks each remote `user` against the shape of your local `user` value. If a remote value does not fit, the client drops it, and the entry keeps the previous `user` value. In development mode, the client then warns one time and names `parseUser`. A `null` inside a remote `user` fits every key, so give each field a fallback when you render it. For the rules, see [Remote user and context](/docs/core/validation#remote-user-and-context).

## Render cost

The hook rerenders only when a peer joins or leaves, or when the `user`, `session`, or `idle` field of a peer changes. A cursor move does not rerender it, because the position is not part of `RemoteUser`.

The list and each unchanged entry keep their object identity. A `React.memo` row, keyed by `clientId`, renders again only for the peer that changed.

## Peer changes

`usePeerChanges(listener)` calls `listener` when a peer joins, leaves, or changes its `user` or `context`. Use it for a one-time effect, such as a notice. For a list, use `useRemoteUsers`.

This component shows the last peer that joined:

```tsx
import { useState } from "react";
import { usePeerChanges } from "@anchor-presence/react";

function JoinNotice() {
  const [notice, setNotice] = useState<string | null>(null);
  usePeerChanges((change) => {
    if (change.type === "join") setNotice(`${change.clientId} joined`);
  });
  return notice !== null ? <p role="status">{notice}</p> : null;
}
```

- The listener receives a `PeerChange`: a `type` of `"join"`, `"update"`, or `"leave"`, the `clientId`, and the `user` and `context` of the peer when they are set. On `"leave"`, `user` and `context` hold the last known values.
- A cursor move never calls the listener. For the rules of each `type`, see [Peer changes](/docs/core/remote-presence#peer-changes).
- The hook subscribes one time per client. An inline listener does not subscribe again on each render, and the hook always calls the listener of the last render.
- The hook returns nothing, so it adds no rerender of its own. Without a client, it calls nothing.
