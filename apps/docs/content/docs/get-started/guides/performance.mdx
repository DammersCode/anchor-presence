Anchor Presence touches layout in one place: the geometry scheduler. The scheduler measures each active anchor at most once per frame, and it does no work while no remote cursor is active. Read this page to plan the size of a room, or to find out why a cursor does not follow a layout change.

## The rule in one sample

After a layout change that the browser does not report, tell the binding:

```ts
binding.invalidate("custom-layout-change");
```

Most apps never need this call. The section [When to call invalidate() yourself](#when-to-call-invalidate-yourself) gives the cases.

## Geometry scheduler model

One shared scheduler runs per client. There is no measurement loop per cursor.

A signal or an `invalidate(reason?)` call marks the layout as dirty. The scheduler combines all calls of one frame into one `requestAnimationFrame` pass, with three phases:

```text
READ PHASE     measure every active anchor once (getBoundingClientRect), plus viewport size
COMPUTE PHASE  resolve every remote cursor from the cached rects
NOTIFY PHASE   publish one immutable snapshot to subscribers
```

An **active anchor** is the anchor that places a current remote cursor. All reads happen before any of your code runs, so one pass causes at most one forced reflow.

## Invalidation signals

While at least one remote cursor is active, the scheduler listens for these signals:

- `resize` on `window`
- `scroll` on `window` and on scrollable parents, through one capture-phase listener on the document
- a `ResizeObserver` on each active anchor and on `document.documentElement`
- one `MutationObserver` on `document.body` (`childList`, `attributes`, `subtree`), for moves with no other signal, such as an inserted sibling or a class change
- a capture-phase scroll listener and a `MutationObserver` on each open shadow root with an active anchor, because document signals stop at shadow boundaries
- the register or unregister of an anchor
- new remote presence data
- the start and end events of CSS transitions and animations
- a call of `invalidate()`

A `ResizeObserver` alone cannot see an element that moves without a size change. The other signals cover that case and keep [invariant 7](/docs/get-started/concepts/how-it-works#the-10-invariants): a local layout change moves a stationary remote cursor without a network message.

### When to call invalidate() yourself

Some layout changes trigger none of the signals. One example is a `style.transform` write in your own `requestAnimationFrame` loop, with no CSS transition. Another example is a layout that a canvas drives. After such a change, call `binding.invalidate()`. Do not call it on every render: the call is cheap, but it adds nothing. See [invalidate](/docs/dom/binding#invalidate).

## Idle behavior

While no remote cursor is active, no `requestAnimationFrame` loop runs. The scheduler disconnects every listener and observer. It reacts to events and never polls. When a remote cursor becomes active, it attaches the signals again.

## Cost per frame and per message

- The scheduler runs at most one pass per frame, and no pass while idle.
- A client publishes at most at 20 Hz while the pointer moves (`publishIntervalMs`, default 50).
- A stationary pointer sends only a heartbeat, every `heartbeatIntervalMs` (default 10 000 ms). The heartbeat carries every field, so a late peer gets the current values.
- The client sends a changed `context` or `user` once. Later messages leave out the fields that did not change.
- The `adaptivePublish` option slows the publish rate while the send buffer of the transport grows. See [Publish rate](/docs/core/presence-client#publish-rate).
- Minified and gzipped, `@anchor-presence/core` is about 10 KB, `@anchor-presence/dom` about 9 KB, and `@anchor-presence/react` about 3 KB. Each size excludes React and the other Anchor Presence packages.

## Scaling limits

A relay forwards each message to every other socket in the room. Relay traffic therefore grows with the number of senders times the number of receivers. The library makes each message smaller, but it cannot reduce the number of copies that the relay sends.

For a large room, use one or more of these measures:

- Split the room into smaller rooms. A room of half the size has about a quarter of the relay traffic.
- Add rate limits and message size caps on the relay.
- Add a server-side aggregator.

The reference relay (`apps/server`) has these limits:

| Limit                  | Setting                   | Default                |
| ---------------------- | ------------------------- | ---------------------- |
| Sockets per room       | `RELAY_MAX_ROOM_SOCKETS`  | 64                     |
| Sockets per server     | `RELAY_MAX_TOTAL_SOCKETS` | 10 000                 |
| Bytes per message      | `MAX_MESSAGE_BYTES`       | 32 KiB                 |
| Rate burst per socket  | `RATE_CAPACITY`           | 80 messages            |
| Rate refill per socket | `RATE_REFILL_PER_SECOND`  | 40 messages per second |

It also checks the origin, checks an optional [room token](/docs/dom/websocket-transport#room-token), and pings each socket. Bun closes a connection with a frame above `maxPayloadLength`: four times `MAX_MESSAGE_BYTES`, or at least 1 MiB.

Scaling across servers and identity checks belong to your server, not to the transport. Each relay keeps its rooms in the memory of one process, so one room must live on one relay process. See [Deploy a relay](/docs/get-started/guides/deploy-relay) and [Identity](/docs/examples/backends/relay-contract#identity).

## Capacity planning

A cursor message with 4 anchors is 292 bytes with `jsonCodec` and 144 bytes with `binaryCodec`. That test message has two-letter anchor IDs, coordinates with one decimal place, and a small `user`. Real coordinates have more decimal places, so a real JSON message is larger. Measure your own messages before you plan.

**Worked example.** A room has 50 clients on `binaryCodec`. 10 of them move the pointer at the same time:

- Each client receives 10 senders × 20 messages/s × 144 bytes ≈ 29 KB/s.
- The relay sends 10 senders × 49 receivers × 20 messages/s × 144 bytes ≈ 1.4 MB/s.

To lower the load of a room:

- Use `binaryCodec` instead of the default `jsonCodec`. See [Codecs](/docs/core/codecs).
- Split a large room into smaller rooms.
- If a room holds more than 64 clients, raise `maxRemoteClients`. See [Remote presence](/docs/core/remote-presence#maxremoteclients).

**Anchor guidance.** Give each element one long-lived anchor ID. Do not create a new ID on each render. In a long list, anchor only the visible rows, and use the list container as the anchor for the rest. Each anchor adds a registry entry and `MutationObserver` work.

## Measured at scale

Two local benchmarks give these numbers: a Chromium receiver test and a relay load test. Plan rooms of up to about 50 active clients per relay process. Before you allow larger rooms, measure your own relay on your own hardware.

<Accordion title="Relay load">

The load test starts the reference relay and opens N WebSocket clients in one room. Each client publishes a real `binaryCodec` cursor message at 20 Hz. The test compares delivery with the rate that the clients really sent, because timers on a busy machine run below 20 Hz. It also measures latency and the CPU and memory of the relay process.

| Clients | Sent (msg/s) | Delivered (msg/s) | Delivery ratio | Latency p50 | Latency p99 | Relay CPU | Relay RSS |
| ------- | ------------ | ----------------- | -------------- | ----------- | ----------- | --------- | --------- |
| 50      | 813          | 39,813            | 100%           | 16 ms       | 32 ms       | 50%       | 66 MB     |
| 100     | 1,963        | 80,408            | 41%            | 3.7 s       | 5.2 s       | 100%      | 70 MB     |
| 200     | 3,950        | 27,656            | 3.5%           | 4.0 s       | 9.4 s       | 98%       | 70 MB     |

- At 50 clients, the relay delivers every message, with a p99 latency of 32 ms and less than one CPU core.
- At 100 clients, the relay must make about 200,000 deliveries per second. The relay process reaches a full CPU core.
- The 100 and 200 rows also show a limit of the test setup. All clients run in one process on the same machine, and that process uses a full CPU core at 100 clients.
- The test raised the socket caps to fit every client. It set the rate limit to a burst of 40 and a refill of 20 messages per second, half the default of the relay.
- The slow-receiver and rate-limit protections did not trigger. Every socket stayed open, and messages queued.
