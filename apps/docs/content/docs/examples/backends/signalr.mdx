Your app runs on ASP.NET Core, and you want presence without a second WebSocket server. `examples/signalr` relays presence through a SignalR hub. A peer is another client in the same room. The hub forwards each message to the peers of the sender and never parses the payload.

The tests of this example use `@microsoft/signalr` 10.0.11 and .NET 10 (`net10.0`).

## Client transport

`createSignalRTransport` takes a plain `@microsoft/signalr` `HubConnection` and wraps it as a `LiveCursorTransport`:

<CodeFromSource repo="examples/signalr/transport.ts" lang="ts" />

Use it like any other transport. The presence client starts the connection:

```ts
import { createPresenceClient } from "@anchor-presence/core";
import { HubConnectionBuilder } from "@microsoft/signalr";
import { createSignalRTransport } from "./transport";

const connection = new HubConnectionBuilder()
  .withUrl("https://your-server.example/hubs/presence?room=main")
  .withAutomaticReconnect()
  .build();

const transport = createSignalRTransport(connection);
const client = createPresenceClient({ transport });
```

<Callout type="warn">
  If you do not call `withAutomaticReconnect()` on the `HubConnectionBuilder`, a dropped connection goes to
  the closed state and never retries.
</Callout>

## Share a use-signalr connection

If your app uses [`use-signalr`](https://www.npmjs.com/package/@dammers/use-signalr-react) for its other hubs, add the presence hub to its contract. Then presence shares the connection, the authentication and the reconnect policy of the app. This sample adds the presence hub to the contract:

```ts
// signalr.ts
import { createSignalRClient, event, method } from "@dammers/use-signalr-react";

export const { SignalRProvider, useSignalR } = createSignalRClient({
  hubs: {
    "/hubs/presence": {
      events: { PresenceReceived: event<[payload: string]>() },
      methods: { OnPresence: method<[payload: string]>() },
    },
    // your app's other hubs
  },
});
```

`useSignalR` gives access to the raw `HubConnection` through `getConnection`. This component creates the presence client on that connection, in the `factory` of a `LiveCursorProvider`:

```tsx
import type { ReactNode } from "react";
import { createPresenceClient } from "@anchor-presence/core";
import { LiveCursorProvider } from "@anchor-presence/react";
import { createSignalRTransport } from "./transport";
import { useSignalR } from "./signalr";

function PresenceProvider({ children }: { children: ReactNode }) {
  const { getConnection } = useSignalR();
  const connection = getConnection("/hubs/presence");
  if (connection === null) return children;
  return (
    <LiveCursorProvider
      clientKey={connection}
      factory={() => {
        const transport = createSignalRTransport(connection);
        // use-signalr owns the connection, so disposing the client must not stop it
        return createPresenceClient({ transport: { ...transport, disconnect: () => {} } });
      }}
    >
      {children}
    </LiveCursorProvider>
  );
}
```

`getConnection` returns `null` until `use-signalr` opens the hub. Until then, the component shows its children without presence. When the hub opens, the children mount again inside the provider, so their local state resets one time.

The provider runs `factory` once per mount and once more for each new connection. It disposes the client on unmount. The empty `disconnect` keeps the shared connection open after the dispose. See [Create the client](/docs/react/client-creation) for the rules of `factory`.

Each `factory` run adds five handlers to the shared connection, and the transport never removes them. As a result, each remount and each Strict Mode double run leave one more set of handlers. A set without a client decodes each message and then drops it.

## Close reasons

The hub refuses a connection with an invalid room name. It first sends a `Refused` message with the code `4007` and the reason `invalid room`. Then it aborts the connection. The transport reports the code through `subscribeClose`:

```ts
client.subscribeClose((close) => {
  if (close.code === 4007) console.warn("The room name is not valid.");
});
```

The hub sends no other close code. It has no auth check and no connection caps. An origin outside the allowlist gets an HTTP `403` before the hub starts, so the transport reports no code for it. `willReconnect` is `true` while `withAutomaticReconnect` retries, and `false` after the connection closes.

## Behavior notes

- The hub adds each connection to a SignalR group for its room. `PresenceHub.OnPresence` forwards to `Clients.OthersInGroup(room)`. As a result, a sender never receives its own message, and other rooms never receive it.
- The hub reads the room from the `room` query parameter of the hub URL. A missing parameter is the room `main`.
- `examples/signalr/signalr-hub.test.ts` starts the real ASP.NET Core hub and runs two clients through it. If `dotnet` is not on `PATH`, the test skips.
- `connection.send` and `connection.on` call a hub method by its name and do not wait for an answer. The hub sends no acknowledgment. The `send` contract of the transport interface needs none.
- `Program.cs` caps an inbound message at 32 KiB through `MaximumReceiveMessageSize`. The cap applies to the base64 text, so the real payload cap is about 24 KiB. SignalR closes the connection on a larger message.
- The hub takes room access control from your ASP.NET Core authentication, for example an `[Authorize]` attribute on `PresenceHub`. It reads no [room token](/docs/dom/websocket-transport#room-token). The hub binds no identity, so a client can claim any `clientId`. See [Security](/docs/get-started/guides/security).

<Callout type="warn">
  If you expose the hub publicly, add a rate limit, for example [ASP.NET Core rate
  limiting](https://learn.microsoft.com/aspnet/core/performance/rate-limit). The hub has no rate limit and no
  connection caps, so one client can flood a room.
</Callout>
