---
title: SSR and Strict Mode
description: How to create a client safely under server rendering and React Strict Mode.
---

No package accesses the DOM at module load time. This page states the one rule that keeps a client safe under server rendering and React Strict Mode: create the client inside `usePresenceClient`, or in an effect, never at module scope in code that also runs on the server.

## Use usePresenceClient

`usePresenceClient` runs its factory once per `key`, in a mount effect, and memoizes the result for the page lifetime:

```tsx
import { createPresenceClient } from "@anchor-presence/core";
import { createWebSocketTransport } from "@anchor-presence/dom";
import { CursorLayer, LiveCursorProvider, usePresenceClient } from "@anchor-presence/react";

function App() {
  const client = usePresenceClient({
    factory: () => {
      const transport = createWebSocketTransport({ path: "/?room=main" });
      transport.connect();
      return createPresenceClient({ transport });
    },
  });
  return (
    <LiveCursorProvider client={client}>
      <CursorLayer />
    </LiveCursorProvider>
  );
}
```

The hook returns `null` until the effect has run, then the same instance across renders and Strict Mode remounts. Server renders return `null` and never run the factory. `LiveCursorProvider` accepts `client={null}` and renders normally, so this pattern is safe end to end.

The factory owns the transport: create it, call `transport.connect()`, then create the client. No part of the library connects a transport for you. `client.dispose()` calls `transport.disconnect()`.

The hook does not call `transport.connect()` itself, and it never disposes the client on unmount. Clients survive route changes and component remounts until the page unloads. Call `client.dispose()` on an explicit user action, such as logout; the call clears the `key` entry, and a later render creates a new client through the factory.

## Why Strict Mode matters here

React Strict Mode, in development, mounts every component twice to surface effects that are not idempotent. A `createPresenceClient` call at module scope, or directly inside a component body, would run twice and create two clients, or connect one transport's socket twice.

`usePresenceClient`'s registry is keyed and lives at module scope, outside the component. The first mount's effect creates the client and stores it under `key`. The second mount's effect sees the existing entry and reuses it. Pass a distinct `key` for a genuinely separate client, for example a second presence room or an admin overlay.

## Two supported SSR patterns

1. Create the client only in browser-only code, for example inside `usePresenceClient` or a plain `useEffect`, and pass `client={null}` until it exists.
2. Pass `client={null}` for the duration of server rendering, and swap in a real client after hydration.

Every hook has a server-safe snapshot: `useRemoteCursors` and `useCursorPresence` return `[]`, `useCursorStatus` returns `"disconnected"`, `useCursorClient` returns `null`, and `useCursorContext` returns `[undefined, setContext]`. `renderToString` works for a tree using every hook with `client={null}`:

```tsx
<LiveCursorProvider client={null}>
  <Dashboard />
</LiveCursorProvider>
```
