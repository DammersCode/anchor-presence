---
title: UI context
description: Opaque context, visibility policies, dialog mismatch handling, and the receiver-UI rule.
---

UI context is application state, such as an open dialog, that a sender attaches to its cursor. A visibility policy on the receiver reads it to show or hide the cursor. Anchor Presence never changes the UI state of the receiver.

## Opaque context

`CursorPresence` carries an optional `context` field. Core treats this field as opaque: it validates its size (max 8 KiB JSON-encoded) and forwards it, but it never reads or interprets its shape.

Set context on the client:

```ts
client.setContext({ route: "/settings", dialog: "invite" });
```

The client sends a change to context once. Full publishes (reconnect and heartbeat) include the current context. A missing field means "unchanged since the previous same-session message". An explicit `null` clears it. On the receiver, context reaches two places: the visibility policy input, and the `context` field on each `ResolvedCursor`.

Use context for information the receiver needs to decide how to show a cursor: current route, open dialog, active tab, or similar semantic state. Do not use context for anything that must stay private. It reaches every receiver in the room when it changes and on full publishes. See [Security](/docs/get-started/guides/security) for validation limits and rendering rules.

## Visibility policies

A visibility policy is a pure function that decides whether a resolved cursor shows:

```ts
type VisibilityPolicy<TContext> = (input: {
  presence: CursorPresence<TContext>;
  resolution: { tier: "anchor" | "viewport" | "hidden"; anchorId: string | null; pointVisible: boolean };
}) => "show" | "hide";
```

The default policy shows cursors at the `anchor` and `viewport` tiers, and hides cursors at the `hidden` tier:

```ts
export const defaultVisibilityPolicy: VisibilityPolicy = ({ resolution }) =>
  resolution.tier === "hidden" ? "hide" : "show";
```

Pass a custom policy through `DomBindingOptions.resolution.visibilityPolicy` (`@anchor-presence/dom`) or `bindingOptions.resolution.visibilityPolicy` on `LiveCursorProvider` (`@anchor-presence/react`). A custom policy can inspect `presence.context` to apply application-specific rules on top of geometric resolution.

A policy can also read `resolution.pointVisible` to hide a cursor clipped by a scroll container. See [Occlusion and scroll](/docs/dom/occlusion-and-scroll) for how the resolver computes it and where the check falls short.

## Dialog mismatch handling

Anchor fallback covers most context mismatches. For example, a sender's cursor sits inside the anchor `settings.dialog.invite`. The receiver has not opened that dialog, so the anchor is absent from its DOM. The fallback chain then moves to a parent anchor, for example `settings`, or to the viewport.

A cursor at the wrong place misleads the receiver. Some cases therefore need an explicit policy instead of geometric fallback. These are three possible approaches:

- **Hide the cursor.** If `presence.context?.dialog` names a dialog that the receiver has not opened, return `"hide"`.
- **Fall back to the dialog trigger anchor.** Register the button that opens the dialog under a stable anchor ID. When the dialog anchor is absent, the fallback chain lands on the trigger button.
- **Show a passive presence indicator.** Do not hide the cursor. Render a muted version for the `hidden` tier, with `tier` and `context` from the resolved cursor.

This policy hides the cursor of a sender whose open dialog differs from the dialog of the receiver:

```ts
const dialogAwarePolicy: VisibilityPolicy<{ dialog?: string }> = ({ presence, resolution }) => {
  const senderDialog = presence.context?.dialog;
  if (senderDialog !== undefined && senderDialog !== myOpenDialogId()) return "hide";
  return resolution.tier === "hidden" ? "hide" : "show";
};
```

## The "never change receiver UI state" rule

Anchor Presence never changes what the receiver's UI shows. Resolving a remote cursor position must not force a route change, open or close a dialog, expand a sidebar, or scroll the page.

This rule keeps the receiving user in full control of their own screen. A remote cursor only gives information. A resolved position can land inside UI that the receiver has not opened. Then the correct response is fallback or hide. Never force that UI open to match the sender.

Do not write code that reacts to `useRemoteCursors()` or `useCursorPresence()` output by mutating local UI state, such as dialogs, routes, or sidebar toggles. Use `context` for display decisions only.
