Anchor Presence needs a bidirectional byte channel between clients: a relay that forwards each message to the peers of the sender. A peer is another client in the same room. `@anchor-presence/core` imports no transport library. Any channel that implements `LiveCursorTransport` works. Pick a backend from the [backend matrix](#backend-matrix).

## What a relay does

A relay does not read the presence protocol. It only forwards bytes between the sockets in one room:

```text
sender.send(bytes) -> relay -> every other socket in the same room -> receiver.subscribe(listener)
```

The reference relay forwards binary frames and does not decode them. It never reads the `anchors`, `context`, or `user` field of a message. It also has caps, a rate limit, an origin check, an optional [room token](/docs/dom/websocket-transport#room-token) check, and a liveness ping. Every relay reads the room from the `room` query parameter, and only the reference relay also reads it from the path. See [Relay contract](/docs/examples/backends/relay-contract#room-from-the-url) for the rules. See [Performance](/docs/get-started/guides/performance#scaling-limits) for how the load of a room-broadcast relay grows with the size of the room.

## The transport interface

Every transport implements `LiveCursorTransport`. Only `send` and `subscribe` are required. See [Transports](/docs/core/transports) for the full interface, its contract, and the shipped WebSocket transport.

### No server

Two options need no relay:

- `createInMemoryPair` from `@anchor-presence/core` connects two transports directly in one process. The code samples of this site use it.
- A `BroadcastChannel` transport connects two tabs or iframes on the same origin. The library does not ship one, so write your own. The live demos of this site use one.

## Choose a backend

- If you run a plain WebSocket server, or you have no server yet, use `createWebSocketTransport` from `@anchor-presence/dom`. It is the only transport that ships in a package. It has reconnect and backoff.
- If your server runs on Bun, Node.js, Hono, or Elysia, use the matching relay example. The client uses `createWebSocketTransport` with no custom transport.
- If your app uses Socket.IO for other real-time features, use the [Socket.IO example](/docs/examples/backends/socketio). Presence then shares that connection, and you need no second WebSocket server.
- If your server runs ASP.NET Core, use the [SignalR example](/docs/examples/backends/signalr). It wraps a `HubConnection` as a transport.
- For a prototype or a test, use `createInMemoryPair` in one process. For two tabs or iframes on the same origin with no server, use a `BroadcastChannel` transport.

## Identity binding

A relay that does not decode messages cannot tell who sent a message. With identity binding, the `authCheck` hook returns a verified `{ clientId, user }`, and the relay writes it into every JSON frame of the connection. [Relay contract](/docs/examples/backends/relay-contract#identity) gives the rules and lists the relays that support it.

The entry files of the Bun, Node.js (ws), Hono and Elysia relays have a demo identity mode. To turn it on, set `RELAY_DEMO_IDENTITY=1` before you start the relay:

```sh
RELAY_DEMO_IDENTITY=1 bun relay.ts
```

In this mode, the [room token](/docs/dom/websocket-transport#room-token) names the user. `authCheck` returns `{ clientId: "user-<token>", user: { name: "<token>" } }`. A client with the room token `ada` gets the `clientId` `user-ada~<connection>` and the user `{ name: "ada" }`. The relay refuses a connection without a room token.

<Callout type="warn">
  If you use the demo identity mode in production, any client can claim any name. The relay trusts the room
  token as the user name. Check the room token in your own `authCheck`, for example as a JWT, and return the
  verified user.
</Callout>

## Conformance suite

`examples/_shared/relay-conformance-suite.ts` is a vitest suite that checks a relay against the relay contract. The Bun, Node.js (ws), Hono and Elysia relays pass the full suite.
