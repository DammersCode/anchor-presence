Core imports no transport library (Invariant 6). An application supplies a transport that implements `LiveCursorTransport`. This page shows the interface, the native WebSocket transport, `createInMemoryPair` for tests and local prototyping, and links to the example adapters.

## The LiveCursorTransport interface

```ts
import type { LiveCursorTransport, ConnectionStatus } from "@anchor-presence/core";

interface LiveCursorTransport {
  connect?(): Promise<void> | void;
  disconnect?(): Promise<void> | void;
  send(data: Uint8Array): Promise<void> | void;
  subscribe(listener: (data: Uint8Array) => void): () => void;
  subscribeStatus?(listener: (status: ConnectionStatus) => void): () => void;
  getStatus?(): ConnectionStatus;
  bufferedBytes?(): number;
}

type ConnectionStatus = "connecting" | "connected" | "reconnecting" | "disconnected";
```

Rules:

- `send` receives already-encoded bytes. The client calls `codec.encode()` before calling `send`.
- `subscribe` receives already-encoded bytes from the wire. The client calls `codec.decode()` and `validatePresence()` after your listener fires.
- `connect`, `disconnect`, `subscribeStatus`, and `getStatus` are optional. When a transport omits `subscribeStatus`, the client reports a constant `"connected"` status.
- `subscribeStatus` should replay the current status to every new subscriber. Without a replay, a client that subscribes after the connection opened never learns it can send. Every example below replays.
- `getStatus` returns the current status. The client reads it once at creation for its initial status; without it, the client starts at `"connecting"` until the first status callback.
- `bufferedBytes` is optional. It reports bytes currently queued by the transport, and is used only by the opt-in `adaptivePublish` client option.
- A `send` failure must not throw past the transport boundary in a way that crashes the app. The client swallows send errors after a status check; presence is lossy by design.

Pass a transport instance to `createPresenceClient`:

```ts
import { createPresenceClient } from "@anchor-presence/core";

const client = createPresenceClient({ transport: myTransport });
```

## Native WebSocket example

`@anchor-presence/dom` ships `createWebSocketTransport`. It reconnects with exponential backoff, and matches the room-broadcast relay in `apps/server/index.ts` in the repository. That relay forwards size- and rate-bounded binary messages to the other sockets in the same room, and enforces a per-room socket cap:

```ts
import { createPresenceClient } from "@anchor-presence/core";
import { createWebSocketTransport } from "@anchor-presence/dom";

const transport = createWebSocketTransport({ path: "/?room=main" });
transport.connect();
const client = createPresenceClient({ transport });
```

The default URL is `ws(s)://<current host>:8787/`. Room grouping is a relay concern, not part of the core protocol. If your relay uses rooms, pass a `url` or `path` such as `/?room=main`. If the relay is started with `RELAY_AUTH_TOKEN`, pass the same value as the `token` option; the transport URL-encodes it and appends it to the upgrade URL as `token=...`. Omit it when the relay has no token configured.

Pass `reconnect: false` to turn off automatic reconnect. Pass `baseBackoffMs` and `maxBackoffMs` to change the backoff, and `random` to inject the jitter source used to spread reconnect attempts. Pass `WebSocketCtor` to inject a WebSocket constructor for tests. The transport also exposes `bufferedBytes()` from `WebSocket.bufferedAmount` for the client's optional adaptive publish rate.

The Socket.IO and SignalR adapters stay in `examples/`. They need foreign dependencies. Only the native WebSocket transport is part of the library.

## createInMemoryPair for tests and prototyping

`@anchor-presence/core` ships `createInMemoryPair`, two transports wired directly to each other in one process:

```ts
import { createInMemoryPair, createPresenceClient } from "@anchor-presence/core";

const { a, b } = createInMemoryPair();
const clientA = createPresenceClient({ transport: a, user: { name: "Alice" } });
const clientB = createPresenceClient({ transport: b, user: { name: "Bob" } });
```

A send from `a` reaches only `b`'s listeners, and a send from `b` reaches only `a`'s. Use it in unit tests, in `renderToString` samples like the ones on this site, and for a quick local check of provider or hook wiring before a relay exists. It cannot cross a process, tab, or iframe boundary: both sides must run in the same JavaScript realm. See [Backends](/docs/examples/backends) for options that do cross that boundary.
