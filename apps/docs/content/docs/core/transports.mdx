A transport is the byte channel between a presence client and the network. `@anchor-presence/core` imports no transport library. You supply a transport that implements `LiveCursorTransport`.

## The LiveCursorTransport interface

`@anchor-presence/core` exports `LiveCursorTransport`, `ConnectionStatus`, and `TransportClose` with these shapes:

```ts
interface LiveCursorTransport {
  connect?(): Promise<void> | void;
  disconnect?(): Promise<void> | void;
  send(data: Uint8Array): Promise<void> | void;
  subscribe(listener: (data: Uint8Array) => void): () => void;
  subscribeStatus?(listener: (status: ConnectionStatus) => void): () => void;
  subscribeClose?(listener: (close: TransportClose) => void): () => void;
  getStatus?(): ConnectionStatus;
  bufferedBytes?(): number;
}

type ConnectionStatus = "connecting" | "connected" | "reconnecting" | "disconnected";

type TransportClose = { code?: number; reason?: string; willReconnect: boolean };
```

Pass a transport instance to `createPresenceClient`:

```ts
import { createPresenceClient } from "@anchor-presence/core";

const client = createPresenceClient({ transport: myTransport });
```

## Connect and disconnect ownership

`connect` and `disconnect` are optional. By default, the client calls `connect()` for you, one time, during creation. If you pass `autoConnect: false`, call `connect()` yourself after you build the transport. You can call it before or after you pass the transport to `createPresenceClient`. See [Presence client](/docs/core/presence-client#connect-the-transport) for both modes.

`client.dispose()` calls `transport.disconnect()` when the transport has one, in both modes. A throwing `disconnect` does not stop the other cleanup of `dispose`.

`send` receives encoded bytes. The client calls `codec.encode()` before it calls `send`. The client catches each throw and each rejection from `send`, because presence is lossy by design. A lost message does not stop the client.

`subscribe` receives encoded bytes from the wire. After your listener receives the bytes, the client calls `codec.decode()` and `validatePresence()`.

## Connection status

`subscribeStatus` and `getStatus` are optional. When a transport omits `subscribeStatus`, the client reports a constant `"connected"` status and never reads `getStatus`.

Replay the current status to every new subscriber inside `subscribeStatus`. Without a replay, a client that subscribes after the connection opened never learns that it can send.

If the transport has `subscribeStatus`, the client reads `getStatus()` one time, at creation, for its first status. Without `getStatus`, the client starts at `"connecting"` until the first status callback arrives.

When the status changes to `connected` from `reconnecting` or `disconnected`, the client publishes its full state again. It also expires each peer that no message confirms, as [After a reconnect](/docs/core/remote-presence#after-a-reconnect) describes. A peer is another client in the same room.

`bufferedBytes` is optional. It reports the number of bytes in the send queue of the transport. The client uses it only for the opt-in `adaptivePublish` option on [Presence client](/docs/core/presence-client#publish-rate).

## Close reasons

`subscribeClose` is optional. A transport that implements it calls each listener each time a connection closes, with a `TransportClose`:

- `code` is the close code, for example `4006` for a rejected token.
- `reason` is the close reason text, when the relay sent one.
- `willReconnect` is `true` when the transport schedules another attempt.

`client.subscribeClose(listener)` forwards the listener to this method. If the transport omits `subscribeClose`, the client never calls the listener. `createWebSocketTransport` implements it. See [Custom transport](/docs/core/custom-transport#close-reasons) for a sketch.
