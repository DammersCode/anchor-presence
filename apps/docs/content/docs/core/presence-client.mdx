`createPresenceClient` builds a `PresenceClient`. The client publishes your local cursor on a timer, and it checks and stores the presence of each peer. A peer is another client in the same room. Create one client for each connection to a room.

The client also sends and receives events: one-shot messages to every peer, for example a reaction. See [Events](/docs/core/events).

## Create a client

This sample creates a client, publishes a cursor, reads the peers, and stops the client:

```ts
import { createPresenceClient } from "@anchor-presence/core";

const client = createPresenceClient({ transport: myTransport, user: { name: "Ada" } });

client.setLocalCursor({ anchors: [{ id: "doc", u: 0.5, v: 0.5 }] });
const unsubscribe = client.subscribeRemote(() => console.log(client.getRemotePresence()));

client.dispose();
```

`transport` is the only required option. See [Transports](/docs/core/transports) for the transport contract, and [Codecs](/docs/core/codecs) for the `codec` option. [`PresenceClientOptions`](/docs/core/api/client#createpresenceclient) lists every option with its default.

`createPresenceClient` throws a `TypeError` when a numeric option is not a finite number. See [createPresenceClient](/docs/core/api/client#createpresenceclient) for the list.

## Connect the transport

The `autoConnect` option decides who calls `transport.connect()`:

<Tabs items={["autoConnect: true (default)", "autoConnect: false"]}>
  <Tab value="autoConnect: true (default)">
    The client calls `transport.connect()` one time, during creation. It subscribes to the messages and the status of the transport first, so it misses no inbound message and no status change.
  </Tab>
  <Tab value="autoConnect: false">
    You call `connect()` yourself, before or right after you create the client:

```ts
const client = createPresenceClient({ transport: myTransport, autoConnect: false });
myTransport.connect();
```

  </Tab>
</Tabs>

A transport with no `connect` method needs no call in either mode. A `connect()` call that throws or rejects never escapes client creation. The transport reports the failure through its own status. `dispose()` calls `transport.disconnect()` in both modes.

## Lifecycle

`client.setLocalCursor(cursor, pointer?)` sets the local cursor position. A `null` cursor clears it for peers. The client does not send on each call. It sends the last value on its next publish tick.

<Callout type="warn">
  If you omit `pointer`, the client keeps the pointer type of the previous call. To send a cursor without a
  pointer type, pass `{}` as `pointer`.
</Callout>

`client.setContext(value)` and `client.setUser(value)` set the values that the client sends to peers. `undefined` clears a value. `getContext()` and `getUser()` return the current local values.

`client.subscribeContext(listener)` calls `listener` on each `setContext` call that changes the value. `client.subscribeUser(listener)` does the same for `setUser`. A call changes the value when `value` is another reference than the current value. The listener receives no argument, so read the value with `getContext()` or `getUser()`. Both methods return a function that removes the listener. The [`useLocalContext`](/docs/react/local-context) and [`useLocalUser`](/docs/react/local-context#local-user) hooks use them.

`client.dispose()` stops the client. It sends a leave message, if the client is connected, and stops every timer. Then it calls `transport.disconnect()` when the transport has one. A disposed client ignores every later call. Create a new client instead.

`client.registerTeardown(fn)` adds a function that `dispose` runs. It returns a function that removes `fn`. If the client is already disposed, `fn` runs at once. The DOM binding uses it, so that `client.dispose()` also stops the binding.

## Status

`client.getStatus()` returns the current `ConnectionStatus`. `client.subscribeStatus(listener)` calls `listener` with each new status, and returns a function that removes the listener. See [Connection status](/docs/core/transports#connection-status) for the values and the transport side.

`client.hasActiveCursors?.()` returns whether at least one peer has a cursor. The method is optional on the `PresenceClient` type. The client from `createPresenceClient` always has it, and the call costs no scan of the peers. The DOM binding uses it to stop frame work in an empty room.

## Leave the room

`client.leave()` tells peers that this client left. Receivers remove the client at once and report a `leave` [peer change](/docs/core/remote-presence#peer-changes). The client stays usable. Its next publish or heartbeat sends the full state, and peers add the client again.

If the client is not connected, `leave()` sends nothing. `dispose()` sends the same leave message before it stops the client. The DOM binding calls `leave()` on the `pagehide` event, so a closed tab disappears from peers at once. See [Page hide](/docs/dom/binding#page-hide).

## Close reasons

`client.subscribeClose(listener)` reports why a connection closed:

```ts
client.subscribeClose((close) => {
  if (!close.willReconnect) showOffline(close.code, close.reason);
});
```

The listener receives a `TransportClose` with the close `code`, the close `reason`, and `willReconnect`. `willReconnect` is `true` when the transport schedules another connection attempt. `subscribeClose` returns a function that removes the listener.

The client gives the listener to the optional `subscribeClose` method of the transport. If the transport has no `subscribeClose`, the listener never runs. `createWebSocketTransport` reports each close. See [Close reasons](/docs/core/transports#close-reasons) for the transport side.

## Publish rate

The client publishes the local cursor every `publishIntervalMs`, `50` by default (`DEFAULT_PUBLISH_INTERVAL_MS`). A publish tick sends a message only when a send is pending. These actions make a send pending:

- A `setLocalCursor` call.
- A reconnect.
- A new peer. See [Late join](/docs/core/remote-presence#late-join).
- A `setContext` or `setUser` call with another reference than the current value. The client does not compare the content, so a new object with equal content also sends a message.

If a send fails while the status is `connected`, the client tries again after 50 ms. Each failure doubles the delay, up to 2 s. If a publish is pending when the page becomes visible again, the client sends it at once.

The `adaptivePublish` option lowers the publish rate while the transport holds many buffered bytes:

```ts
const client = createPresenceClient({
  transport: myTransport,
  adaptivePublish: { highWatermarkBytes: 64 * 1024 },
});
```

| Field                   | Default                           | Effect                                     |
| ----------------------- | --------------------------------- | ------------------------------------------ |
| `highWatermarkBytes`    | `64 * 1024`                       | Buffered bytes that turn on the slow rate. |
| `lowWatermarkBytes`     | half of `highWatermarkBytes`      | Buffered bytes that turn it off again.     |
| `slowPublishIntervalMs` | `max(publishIntervalMs * 4, 100)` | The publish interval at the slow rate.     |

The client reads buffered bytes through the optional `bufferedBytes()` method of the transport. Without that method, `adaptivePublish` has no effect.

## Heartbeat

A heartbeat is a full-state message that the client sends every `heartbeatIntervalMs`, `10000` by default (`DEFAULT_HEARTBEAT_INTERVAL_MS`). The client sends it even when nothing changed. As a result, the [stale timeout](/docs/core/remote-presence#stale-timeout) of a peer does not remove a client that changes nothing.

## IDs

Every client has a `clientId` and a `session`. Pass `clientId` to keep one ID for a client instance. The client creates a new `session` for each client and never uses it again.

Both IDs come from `idFactory`. The default `idFactory` returns 12 URL-safe characters with 72 random bits from `crypto.getRandomValues`. If `crypto.getRandomValues` is missing, it builds the ID from the time and `Math.random`.

This client uses UUIDs:

```ts
const client = createPresenceClient({
  transport: myTransport,
  idFactory: () => crypto.randomUUID(),
});
```

<Callout type="warn">
  If the page loads over plain HTTP from a host other than `localhost`, `crypto.randomUUID` is missing and
  this `idFactory` throws. The default `idFactory` works on plain HTTP.
</Callout>

<Callout type="warn">
  If `idFactory` returns IDs longer than 64 characters, receivers drop every message of the client. The
  default limits allow 128 characters for `clientId` and 64 for `session`.
</Callout>

## Development mode

`isDevMode()` returns whether the code runs in development mode. It applies these rules in order:

1. If `import.meta.env.DEV` is `false`, it returns `false`.
2. If `process.env.NODE_ENV` is `"production"`, it returns `false`.
3. In all other cases, it returns `true`. This includes a read that throws.

This sample shows debug output only in development:

```ts
import { isDevMode } from "@anchor-presence/core";

if (isDevMode()) console.debug("[presence] debug overlay on");
```

The client reads development mode one time, at creation. In development mode, it writes console warnings that start with `[anchor-presence]`. A receiver drops a bad message or field without a warning in production.

<Accordions>
  <Accordion title="Warnings of the client">

    - An outbound `context`, `user`, or whole message breaks the size limit. The client checks at creation and on each `setContext` or `setUser` call that changes the value. It warns on each check that finds a value over the limit.
    - A remote `user` or `context` arrives and no check applies. The client warns one time.
    - The shape check drops a remote `user` or `context`. The warning names `parseUser` or `parseContext`. The client warns one time for `user` and one time for `context`.
    - The shape check keeps a remote `user` or `context`, but drops a key that the local value does not have, for example a nested object. The page warns one time, for all clients together.
    - The store is full and drops a new peer. The client warns one time.
    - The client drops an inbound message because it is too large, does not decode or validate, or a subscriber throws. The client warns one time for each reason.
    - Another client uses the same `clientId`. The page warns one time, for all clients together.
    - `staleTimeoutMs` is at most twice `heartbeatIntervalMs`, so a quiet peer expires between two heartbeats. The page warns one time, for all clients together.
    - The codec cannot encode the `user` or `context`. The client sends the cursor without them, and the page warns one time.
    - A message fails to encode or to send for another reason. The client warns one time.
    - A `subscribeContext`, `subscribeUser`, `subscribeRemote`, or `subscribePeers` listener throws. The client writes the error with `console.error` and calls the other listeners. A throwing `subscribeEvents` listener gives no output.

  </Accordion>

  </Accordions>
