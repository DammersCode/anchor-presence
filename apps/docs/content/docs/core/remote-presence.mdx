`RemotePresenceStore` holds the presence of every peer that a client accepts. `createPresenceClient` creates one store for each client. Read the store through the client to render peers, or use the store alone on a relay or in a test.

## Read remote presence

This sample reads the stable snapshot and logs it on each change:

```ts
const remotePresences = client.getRemotePresence();
const unsubscribe = client.subscribeRemote(() => {
  console.log(client.getRemotePresence());
});
```

`getRemotePresence()` returns the stable snapshot: a `RemotePresence[]` without the `sequence` field. The store keeps the array and the identity of each entry while nothing observable changes. As a result, the stable snapshot fits a render loop or a `useSyncExternalStore` subscription.

`getRemoteSnapshot()` returns the raw snapshot, with `sequence`. It returns a new array on every accepted message. Use it to watch sequence numbers, not for rendering.

## The life of a peer

A peer joins on its first accepted message. It goes idle when its presence stops changing, and it leaves on a leave message or a timeout:

  chart={`stateDiagram-v2

  [*] --> active: first message
  active --> idle: idleAfterMs, no change
  idle --> active: presence changes
  active --> [*]: leave or timeout
  idle --> [*]: leave or timeout`}
/>

## Stale timeout

The store removes a peer when it accepts no message from that peer for `staleTimeoutMs`. The default is `DEFAULT_STALE_TIMEOUT_MS`, `70000` milliseconds. Set `staleTimeoutMs` on `createPresenceClient` to change it. The client enforces a minimum of `1000` milliseconds.

## Idle state

The store sets `idle: true` on the `RemotePresence` of a peer whose presence did not change for `idleAfterMs`. The store measures this time from the last change, not from the last message. The default is `DEFAULT_IDLE_AFTER_MS`, `15000` milliseconds. `idleAfterMs` always stays below `staleTimeoutMs`. If you pass a larger value, the store clamps it to `staleTimeoutMs - 1`.

Heartbeats do not end the idle state, because they repeat the same state. A peer that changes nothing goes idle while its heartbeats keep arriving. Any change in cursor, user, context, or pointer type ends it. Use `idle` to dim a cursor that stopped moving. `staleTimeoutMs` decides when the cursor disappears.

## Peer changes

`client.subscribePeers(listener)` reports when peers join, leave, or change their profile:

```ts
const unsubscribe = client.subscribePeers((change) => {
  if (change.type === "join") showToast(`${change.clientId} joined`);
});
```

The listener receives a `PeerChange` with a `type`, the `clientId` of the peer, and its `user` and `context` when set:

| `type`   | When the store reports it                                                                |
| -------- | ---------------------------------------------------------------------------------------- |
| `join`   | The store accepts the first message of an unknown `clientId`.                            |
| `update` | The `user` or `context` of a known peer changes.                                         |
| `leave`  | The store removes the peer: a leave message, the stale timeout, or the reconnect expiry. |

These rules decide the edge cases:

- Cursor moves, pointer changes, and events never produce a change.
- A heartbeat that repeats an equal `user` or `context` produces no `update`.
- A message from a known `clientId` with another `session` produces no `join`. It produces an `update` when its `user` or `context` differs by value from the stored one.
- A message that the store drops because it is full produces no `join`.

In React, [`usePeerChanges`](/docs/react/remote-users#peer-changes) wraps this method.

## Leave messages

A client sends a leave message when you call `client.leave()` or `client.dispose()`. See [Leave the room](/docs/core/presence-client#leave-the-room). Receivers remove the client at once. They do not wait for `staleTimeoutMs`.

A receiver accepts a leave message only from the stored `session`, and only with a higher `sequence`. A leave message for an unknown `clientId` changes nothing.

## Late join

When the client accepts the first message of an unknown `clientId`, it answers with one full publish. A known `clientId` with another `session` gets the same answer. The full publish carries the cursor, `user`, and `context`. As a result, the peer that joined sees this client before the next heartbeat.

The answer waits a random delay of up to 500 ms, then goes out on the next publish tick. One delay covers every peer that joins in this time, and the random delay spreads the answers of the clients in a full room. A leave message or an event gets no answer.

## After a reconnect

When the status changes to `connected` from `reconnecting` or `disconnected`, the client marks every peer unconfirmed. A peer can leave during the outage, and its leave message never reaches this client.

Any accepted message confirms a peer. If an unconfirmed peer sends no message within `2 * heartbeatIntervalMs + 5 s`, the next sweep removes it and reports a `leave`. A sweep is a periodic check of the store. With the default `heartbeatIntervalMs`, this time is 25 seconds. If the stale timeout comes first, the stale timeout applies. A peer that stays in the store shows its last cursor again as soon as the status is `connected`. See [Connection status](/docs/dom/binding#connection-status).

<Callout type="warn">
  If peers use a longer `heartbeatIntervalMs` than this client, they disappear after a reconnect until their
  next message. The client uses its own `heartbeatIntervalMs` for this time.
</Callout>

## maxRemoteClients

`maxRemoteClients` caps the number of peers that the store tracks. The default is `64` (`DEFAULT_MAX_REMOTE_CLIENTS`). When the store is full, it drops each message from a new `clientId`. Known peers keep their updates.

<Callout type="warn">
  If a room can hold more than 64 clients, raise `maxRemoteClients`. Otherwise the clients above the cap never
  appear. In a production build, nothing reports the drop unless you pass `onRemoteClientRejected`.
</Callout>

This client raises the cap and reports each dropped peer:

```ts
const client = createPresenceClient({
  transport: myTransport,
  maxRemoteClients: 200,
  onRemoteClientRejected: ({ clientId }) => reportMetric("presence.remote_client_dropped", clientId),
});
```

`onRemoteClientRejected` runs each time the store drops a new peer because it is full. It receives `{ clientId }`, the ID of the dropped peer. If it throws, the client ignores the error. See [capacity planning](/docs/get-started/guides/performance#capacity-planning).

## Message ordering

The store drops a same-session message whose `sequence` is not higher than the stored value. As a result, an out-of-order or duplicate delivery never moves a cursor backward. A message from a new `session` for a known `clientId` always replaces the stored value. This rule covers a client that reconnects with a new session ID.

## Use the store without a client

`RemotePresenceStore` is exported, so a relay or a test can hold remote presence without a `PresenceClient`. This sample checks each decoded message, stores it, and runs the sweep on a timer:

```ts
import { RemotePresenceStore, validatePresence } from "@anchor-presence/core";

const store = new RemotePresenceStore({ maxRemoteClients: 200 });
const sweepTimer = setInterval(() => store.sweep(), 1000);

function receive(decoded: unknown) {
  const presence = validatePresence(decoded);
  if (presence !== null && presence.event === undefined) store.ingest(presence);
}
```

The store has no timer of its own. Without a `sweep()` call on a timer, no peer goes stale or idle.

`ingest` does not check a message. Before you call `ingest`, do the steps that the client does:

1. Pass the decoded value through `validatePresence`.
2. Drop the echoes of your own `clientId`.
3. Keep event messages out of the store. An event message has a `null` cursor, so `ingest` stores it as a peer without a cursor.

The constructor takes [`RemotePresenceStoreOptions`](/docs/core/api/client#remotepresencestore). Its `staleTimeoutMs` has no minimum, unlike the client option. `onRemoteClientRejected` runs each time the full store drops a message from a new peer.

The store has these methods:

| Method                           | Effect                                                                                                               |
| -------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| `ingest(presence)`               | Applies one checked message. Returns `true` when the store accepts it. The ordering and leave rules above apply.     |
| `sweep()`                        | Removes stale peers and sets or clears `idle`.                                                                       |
| `remove(clientId)`               | Removes one peer and reports a `leave`. An unknown `clientId` changes nothing.                                       |
| `has(clientId, session?)`        | Returns whether the store holds the peer, with this `session` when you pass one.                                     |
| `expireUnlessRefreshed(graceMs)` | Marks every peer unconfirmed. A later `sweep` removes each peer that sends no message within `graceMs`.              |
| `subscribe(listener)`            | Calls `listener` on each accepted message, each removal, and each `idle` change. Returns a function that removes it. |
| `subscribePeers(listener)`       | Calls `listener` with a `PeerChange`. Returns a function that removes it.                                            |
| `getSnapshot()`                  | Returns the raw snapshot, with `sequence`.                                                                           |
| `getStableSnapshot()`            | Returns the stable snapshot, with `idle` and without `sequence`.                                                     |
| `hasActiveCursors()`             | Returns whether at least one peer has a cursor. The store keeps a count, so this check costs no scan.                |
