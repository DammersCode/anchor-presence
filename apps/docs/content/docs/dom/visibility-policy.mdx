A `VisibilityPolicy` is a function that decides whether a resolved cursor renders. It returns `"show"` or `"hide"`, and the result goes into `ResolvedCursor.visible`. A custom policy can hide cursors by role, by UI mode, or for a point that a scroll container clips.

This policy hides the cursors of staff users:

```ts
import type { VisibilityPolicy } from "@anchor-presence/dom";

const hideStaffCursors: VisibilityPolicy<{ role: string }> = ({ presence }) =>
  presence.context?.role === "staff" ? "hide" : "show";
```

## The default policy

If you do not set `resolution.visibilityPolicy`, `createDomBinding` uses a default policy with this logic:

```ts
const defaultVisibilityPolicy: VisibilityPolicy = ({ resolution }) =>
  resolution.tier === "hidden" ? "hide" : "show";
```

`@anchor-presence/dom` does not export the default policy. The default policy hides a cursor only when nothing resolved. It shows an `anchor` or `viewport` tier cursor even when the point sits in a clipped region. See [Occlusion and scroll](/docs/dom/occlusion-and-scroll) for a policy that also hides a clipped point.

## Write a custom policy

Each time the resolver resolves the cursors, it calls the policy once for each peer. The policy receives two values:

- `presence`: the full presence of the peer, with its `context` and `user`.
- `resolution`: the `tier`, the winning `anchorId`, and `pointVisible`.

The first type parameter of `VisibilityPolicy` is the context type, and the second is the user type. Pass the policy through `resolution.visibilityPolicy`. The client must have the same context type as the policy:

```ts
import { createPresenceClient } from "@anchor-presence/core";
import { createDomBinding } from "@anchor-presence/dom";

const client = createPresenceClient<{ role: string }>({ transport: myTransport });
const binding = createDomBinding(client, {
  resolution: { visibilityPolicy: hideStaffCursors },
});
```

<Callout type="warn">
  If you use a policy for access control, it gives no protection. The sender sets `context`, and nothing
  authenticates it. A policy only hides a cursor on the receiver. See
  [Security](/docs/get-started/guides/security).
</Callout>

See [UI context](/docs/get-started/concepts/ui-context) for policies that compare the UI state of the sender and the receiver.

## Run the policy again after a state change

A policy can read state that is not part of the presence, for example the dialog that the receiver has open. The binding runs the policy only when it resolves the cursors again. If that state changes while no cursor moves, each cursor keeps its old visibility. For this reason, call `binding.invalidate()` after each change of the state that the policy reads.

This policy reads a variable, and the setter of the variable calls `invalidate`:

```ts
let openDialog: string | null = null;

const dialogPolicy: VisibilityPolicy<{ dialog?: string }> = ({ presence, resolution }) => {
  const senderDialog = presence.context?.dialog;
  if (typeof senderDialog === "string" && senderDialog !== openDialog) return "hide";
  return resolution.tier === "hidden" ? "hide" : "show";
};

function setOpenDialog(next: string | null) {
  openDialog = next;
  binding.invalidate("dialog-changed");
}
```

In React, `useCursorBinding` returns the binding of the nearest `LiveCursorProvider`. This component writes the open dialog into the variable of the policy, then calls `invalidate`:

```tsx
import { useEffect } from "react";
import { useCursorBinding } from "@anchor-presence/react";

function SyncOpenDialog({ dialog }: { dialog: string | null }) {
  const cursorBinding = useCursorBinding();
  useEffect(() => {
    openDialog = dialog;
    cursorBinding?.invalidate("dialog-changed");
  }, [cursorBinding, dialog]);
  return null;
}
```

If a policy throws, the binding keeps the last snapshot. See [Errors in a policy or interpolator](/docs/dom/binding#errors-in-a-policy-or-interpolator).
