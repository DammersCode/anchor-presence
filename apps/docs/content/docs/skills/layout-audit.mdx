The layout audit skill measures how far a remote cursor can jump when the layout of your app changes. Examples are a sidebar that collapses, a table that becomes cards, and a breakpoint that reflows a grid. To use it, install the skill and ask your agent to audit your layouts. The agent opens your running app in a real browser. It gives back a score for each view pair, with concrete fixes.

## What it does

The agent scans your code for anchors, routes, breakpoints, and toggles, such as a collapsible sidebar or a dialog. An anchor is an element marked with `data-anchor`. The agent builds a list of views. A view is one route at one viewport width in one UI state. Then the agent measures every pair of views of the same page in a real browser. Each pair gets a score from 0 (low risk) to 100 (high risk), broken into five sub-scores.

If a pair scores moderate or high, the agent proposes fixes with the file and line. It applies only the fixes that you pick.

## When to use it

| Situation                                                            |                                Use it                                |
| -------------------------------------------------------------------- | :------------------------------------------------------------------: |
| Before you ship a responsive or collapsible layout with live cursors |                                 Yes                                  |
| Remote cursors jump between two layouts                              |                                 Yes                                  |
| You review a layout for live presence risk                           |                                 Yes                                  |
| You add live cursors for the first time                              |   No. Use the [integration skill](/docs/skills/integration) first.   |
| A single cursor never appears                                        | No. See [Troubleshooting](/docs/get-started/guides/troubleshooting). |

## Prerequisites

| Requirement            | Detail                                                                                                           |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Running app            | A local or deployed URL that answers with HTTP 200.                                                              |
| Playwright             | The skill checks for Playwright. If it is missing, the skill gives the install command for your package manager. |
| Node                   | Version 20 or later.                                                                                             |
| Anchors already placed | The audit measures the anchors that your app already has. If your app has none, run the integration skill first. |

## What it asks you

| Question               | Options                                                                      | Default                                                    |
| ---------------------- | ---------------------------------------------------------------------------- | ---------------------------------------------------------- |
| URL of the running app | Any HTTP URL. As an alternative, the agent starts the dev script.            | None. The agent asks, because the code cannot answer this. |
| Views to measure       | Confirm, remove, or add rows in the proposed route × viewport × state matrix | The proposed matrix, after you confirm it                  |
| Report format          | `table`, `markdown`, `mermaid`, or a comma-separated combination             | `table`                                                    |
| Which fixes to apply   | Pick fixes by number from the proposals for each view pair                   | None. The agent applies no fix until you pick one.         |

## How it works

<Steps>
  <Step>
    **Scan.** The agent finds every `data-anchor` in your code and the routes that render them. It also finds
    your breakpoints and the toggles that change which anchors show or where they sit.
  </Step>
  <Step>
    **Propose a matrix.** It builds views from routes, viewport widths, and states. The widths are a base set
    plus your breakpoints. The states are the default state plus one state for each toggle. Before it
    measures, it shows you the number of pairs.
  </Step>
  <Step>**Check prerequisites.** It checks that the app URL answers and that Playwright is installed.</Step>
  <Step>
    **Measure.** It opens each view in a real browser, records the anchor boxes, and scores every pair.
  </Step>
  <Step>
    **Report.** It asks which format you prefer. Then it shows the results or writes them to a file.
  </Step>
  <Step>
    **Propose fixes.** For each pair that scores moderate or high, it matches the worst sub-scores to a fix.
    It cites the file and line.
  </Step>
  <Step>
    **Apply and measure again.** It applies only the fixes that you pick. Then it measures again and shows a
    before-and-after table.
  </Step>
</Steps>

## Output formats

| Format      | Content                                                                                   | Rough chat cost                                                |
| ----------- | ----------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| `table`     | One row per view pair (top 15): total, band, five sub-scores                              | About 40 tokens per row, 600 for 15 rows                       |
| `markdown`  | A file: the score table, then per pair the inputs, largest jumps, gaps, shapes, fallbacks | About 30 tokens for the path. The script prints the file size. |
| `mermaid`   | A file: bar charts of total and jump distance per pair, plus fallback-chain flowcharts    | About 30 tokens for the path                                   |
| Combination | `table,markdown`, `markdown,mermaid`, or `all`                                            | The sum of the parts. The files merge into one file.           |

## Score bands

Each sub-score goes from 0 to 100. It is 0 at or below the first value, 100 at or above the second, and linear in between:

| Sub-score | Weight | What it measures                                                         | 0 at        | 100 at                          |
| --------- | :----: | ------------------------------------------------------------------------ | ----------- | ------------------------------- |
| Jump      |  35%   | How far apart two neighboring anchors land in the other view (90th pct.) | 40 px       | 240 px                          |
| Gap       |  25%   | Share of a container where the pointer has no anchored parent            | 5%          | 40%                             |
| Depth     |  15%   | How many levels an anchor falls back in the other view                   | 0           | `maxAnchors` levels (default 4) |
| Aspect    |  15%   | How much an anchor's width-to-height ratio changes (90th pct.)           | 1.3 × ratio | 3 × ratio                       |
| Parity    |  10%   | Share of anchor IDs that exist in one view only                          | 0%          | 100%                            |

`maxAnchors` is the audit config key for the length of the anchor chain that the app's binding sends. Set it to the `maxSentAnchors` option of your binding. At depth `maxAnchors`, the anchor falls back to the viewport.

By default, Jump measures in CSS pixels. You can set `"jumpScale": "viewport"` in the audit config. Then Jump measures each jump as a percent of the viewport width of the receiving client. The range is 3.125% to 18.75%. These values equal 40 px and 240 px on a 1280 px screen. As a result, the same jump scores higher on a phone than on a desktop.

The total is the weighted sum, but never lower than Jump or Gap. Users see a large jump or a large gap on its own, so the other sub-scores cannot dilute it.

| Total  | Band     |
| ------ | -------- |
| 0–20   | Low      |
| 21–50  | Moderate |
| 51–100 | High     |

See [Scoring a view pair](https://github.com/DammersCode/anchor-presence/blob/main/skills/anchor-presence-audit/scoring.md) in the skill source for the exact formula.

## Common questions

<Accordions type="multiple">
<Accordion title="Does it need my app in production?">
No. Point it at any running instance, including `localhost`. Nothing it measures leaves your machine.
</Accordion>
<Accordion title="What if I have no Playwright installed?">
The skill detects this and gives you the exact install command for your package manager. It asks before it installs anything.
</Accordion>
<Accordion title="Can I run this in CI?">
Yes. Run `measure.mjs` with `--fail-above <score>`. If any view pair scores above that value, the script exits with code 1. If the script cannot measure a view, it also exits with code 1. As a result, a pipeline fails the build on a regression or on an app that did not start.
</Accordion>
<Accordion title="Does it fix things automatically?">
No. It proposes fixes for each pair and applies only the ones that you pick, one round per run.
</Accordion>
<Accordion title="What counts as one view?">
One route, at one viewport width, in one UI state. For example, the orders page at 768 px with the sidebar collapsed.
</Accordion>
</Accordions>

## It works if

- The measurement summary reports every view measured (`Measured N/N views`).
- Every pair that scores moderate or high has a proposal, or a stated reason why no fix applies.
- After you apply fixes, the before-and-after table shows lower totals for the pairs that you picked. No pair gets worse without a note.
- A CI run with `--fail-above` exits with code 0 after every pair is at or below your threshold.
