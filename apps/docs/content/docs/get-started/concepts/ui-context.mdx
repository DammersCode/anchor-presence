UI context is app state that a sender attaches to its cursor, for example the open dialog or the route. A visibility policy on the receiver reads that context and shows or hides the cursor. Use context when the anchor alone cannot tell whether a cursor makes sense on the receiver. Anchor Presence never changes the UI state of the receiver.

## Where context comes from

The sender sets it with `setContext` on the client, or with `useLocalContext` in React. The steps are on [Local context and user](/docs/react/local-context), and the [Typing and away](/docs/get-started/guides/typing-and-away) recipe has a full example. On the receiver, the context reaches the visibility policy and the `context` field of each `ResolvedCursor`.

## What the client sends

The `context` field of `PresenceMessage` is opaque: `@anchor-presence/core` gives it no meaning.

- The client sends a changed context once. Later messages leave the field out, which means "unchanged".
- Reconnect and heartbeat messages carry the current context, so a late peer gets it.
- `setContext(undefined)` sends `null`, which clears the context on every peer.
- The receiver drops a context above 8 KiB of JSON. If the receiver has a local context, it also checks the shape of each remote context. See [Remote user and context](/docs/core/validation#remote-user-and-context).

<Callout type="warn">If you put private data in context, every peer in the room gets it.</Callout>

## Visibility policies

A visibility policy is a pure function that decides whether a resolved cursor shows:

```ts
type VisibilityPolicy<TContext = unknown, TUser = unknown> = (input: {
  presence: PresenceMessage<TContext, TUser>;
  resolution: { tier: ResolutionTier; anchorId: string | null; pointVisible: boolean };
}) => "show" | "hide";
```

`ResolutionTier` is `"anchor" | "viewport" | "hidden"`. The default policy hides only the `hidden` tier. `pointVisible` is `false` when a scroll container clips the point. See [Occlusion and scroll](/docs/dom/occlusion-and-scroll).

Pass a custom policy in `resolution.visibilityPolicy` of the binding options. In React, pass it in `bindingOptions` of `PresenceProvider`. [Visibility policy](/docs/dom/visibility-policy) has the full reference.

## Dialog mismatch handling

The cursor of a sender can sit inside the anchor `settings.dialog.invite`. If that dialog is closed on the receiver, the fallback chain moves to a parent anchor, for example `settings`. A cursor at that place can mislead the receiver. Pick one of three approaches:

- **Hide the cursor.** If `presence.context?.dialog` names a dialog that is closed on the receiver, return `"hide"`.
- **Fall back to the dialog trigger.** Give the button that opens the dialog a stable anchor ID. Then the fallback chain lands on that button.
- **Show a muted cursor.** Keep the cursor, and render a muted version from the `tier` and `context` of the resolved cursor.

This policy hides the cursor of a sender whose `dialog` context is not the dialog that is open on the receiver:

```ts
const dialogAwarePolicy: VisibilityPolicy<{ dialog?: string }> = ({ presence, resolution }) => {
  const senderDialog = presence.context?.dialog;
  if (typeof senderDialog === "string" && senderDialog !== myOpenDialogId()) return "hide";
  return resolution.tier === "hidden" ? "hide" : "show";
};
```

The client needs the same context type as the policy, for example `createPresenceClient<{ dialog?: string }>`. The binding cannot see the open dialog of the receiver. When it changes, call `binding.invalidate()` to run the policy again. See [Run the policy again after a state change](/docs/dom/visibility-policy#run-the-policy-again-after-a-state-change).

## Never change the receiver UI

A remote cursor only gives information. It must not change a route, open or close a dialog, expand a sidebar, or scroll the page of the receiver. If a cursor points into UI that is closed on the receiver, fall back or hide the cursor.

Do not change local UI state as a reaction to `useRemoteCursors()` or `useRemotePresence()`. Use `context` to decide how to show a cursor, nothing more. [Follow mode](/docs/get-started/guides/follow-mode) is the one exception: the user asks to follow a peer, so a scroll is the expected result.
