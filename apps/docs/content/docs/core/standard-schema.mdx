Remote data is untrusted. The client checks its size and structure, but it cannot know the shape of your `user`, your `context`, or your events. Use a schema to check that shape. Valibot, Zod, and ArkType are tested. Other libraries that implement [Standard Schema](https://standardschema.dev) fit the same interface. No test covers them.

The schema support is optional. Without it, `user` and `context` stay `unknown`, and the client keeps its default shape check. Core adds no dependency. The helper lives in its own entry point, `@anchor-presence/core/standard-schema`, so an app that does not import it pays nothing.

## Check the user and the context

This client drops a remote `user` or `context` that the schema rejects:

```ts
import { createPresenceClient } from "@anchor-presence/core";
import { parserFrom } from "@anchor-presence/core/standard-schema";
import * as v from "valibot";

const User = v.object({ name: v.string(), color: v.string() });
const Context = v.object({ typingIn: v.nullable(v.string()) });

const client = createPresenceClient({
  transport,
  user: { name: "Ada", color: "#4f46e5" },
  parseUser: parserFrom(User),
  parseContext: parserFrom(Context),
});
```

`parserFrom` returns a function for the `parseUser` or `parseContext` option. The client takes its types from these two functions. `client.getRemotePresence()` returns the `user` and `context` with the output types of the schemas.

The local `user` that you pass must have the output type of its schema.

## Types without a schema

The client takes the type of `user` and `context` only from `parseUser` and `parseContext`. A type argument alone is a compile error. Without a parser, both types are `unknown`. The default shape check is a runtime guard. It never types the value.

This client has no parser, so `user` and `context` are `unknown`:

```ts
import { createPresenceClient } from "@anchor-presence/core";

const client = createPresenceClient({ transport, user: { name: "Ada" } });
const remote = client.getRemotePresence()[0];
const user: unknown = remote?.user;
```

Check an `unknown` value before you use it. To type it, pass a parser.

## Check the events

This client drops an event with an unknown type, or with data that its schema rejects:

```ts
import { createPresenceClient } from "@anchor-presence/core";
import { eventParserFrom } from "@anchor-presence/core/standard-schema";
import { z } from "zod";

const parseEvent = eventParserFrom({
  chat: z.object({ text: z.string().max(200) }),
  wave: null,
});

const client = createPresenceClient({ transport, parseEvent });
```

Use `null` for an event without data. The events that `client.subscribeEvents` delivers have the types of the schemas. For a typed `send`, see [Events](/docs/core/events).

## See why a value was dropped

When the schema rejects a value, the client drops that field or event. A peer that runs an older version of your app can lose its `user` this way. The cursor of that peer stays. To see the drops, pass `onInvalid`. Its signature is `onInvalid(issues, value)`. `parserFrom(schema, options?)` and `eventParserFrom(schemas, options?)` both take it in `options`:

```ts
const parseUser = parserFrom(User, {
  onInvalid: (issues) => console.warn("dropped a user", issues[0]?.message),
});
```

## Limits

- The schema must validate in a synchronous way. A schema that returns a promise drops every value, and `parserFrom` warns once, also in production.
- The client runs your schema after `validatePresence`. A schema never sees a message above the size and depth limits. See [Validation](/docs/core/validation).
- A peer runs the same schema on your output. If a schema transforms its value into something its own input does not accept, the peer drops it. Pass `onInvalid` to see these drops.
- A value that a schema turns into `undefined` counts as rejected, because `undefined` means a drop.
- The entry point has no `node10` module resolution. Use `node16`, `nodenext`, or `bundler`.
