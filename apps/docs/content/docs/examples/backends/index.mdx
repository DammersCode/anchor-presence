Live cursors need a relay: a server that forwards each message to the peers of the sender. `@anchor-presence/core` imports no transport library, so any channel that implements `LiveCursorTransport` works. This section has one tested relay for each common backend.

This table compares the relays. "Topics" means that the runtime forwards a message to every subscriber of the room topic. "Room loop" means that the relay keeps a set of sockets per room and sends to each one:

| Relay        | Runtime        | Library                  | Fan-out               | Pick it when                                         |
| ------------ | -------------- | ------------------------ | --------------------- | ---------------------------------------------------- |
| Bun          | Bun            | none (`Bun.serve`)       | Topics (`ws.publish`) | You run Bun and want the least code.                 |
| Node.js (ws) | Node.js or Bun | `ws` over `node:http`    | Room loop             | You run Node.js, or you need a soft slow-peer limit. |
| Hono         | Bun            | `hono` (`hono/bun`)      | Topics (`ws.publish`) | You already route HTTP with Hono.                    |
| Elysia       | Bun            | `elysia`, `@elysia/eden` | Topics (`ws.publish`) | You use Elysia and want a typed client.              |
| Socket.IO    | Node.js or Bun | `socket.io`              | Socket.IO rooms       | Your app already uses Socket.IO.                     |
| SignalR      | .NET 10        | ASP.NET Core SignalR     | SignalR groups        | Your server runs ASP.NET Core.                       |

The Bun, Node.js (ws), Hono and Elysia relays need no custom client transport. The client connects with `createWebSocketTransport` from `@anchor-presence/dom`. Socket.IO and SignalR need the client transport of their example.

To run a relay in production, see [Deploy a relay](/docs/get-started/guides/deploy-relay).

Every relay has an integration test that starts the real server and connects two clients. The Bun, Node.js (ws), Hono and Elysia relays also pass the [conformance suite](#conformance-suite).

## No server

Two transports need no relay:

- `createInMemoryPair` from `@anchor-presence/core` connects two transports in one process. Use it for tests and prototypes. The code samples of this site use it.
- `createBroadcastChannelTransport` from `@anchor-presence/dom` connects tabs and iframes on the same origin. The live demos of this site use it.

## What a relay does

A relay does not read the presence protocol. It forwards bytes between the sockets of one room:

```text
sender.send(bytes) -> relay -> every other socket in the same room -> receiver.subscribe(listener)
```

The relay never reads the `anchors`, `context`, or `user` field of a message. It only decodes a message when [identity binding](#identity-binding) is on. Every relay page has the same three behavior tables: what the relay does, its limits, and its auth checks. [Relay contract](/docs/examples/backends/relay-contract) gives the rules that every relay must obey. [Performance](/docs/get-started/guides/performance#scaling-limits) shows how the load of a relay grows with the size of a room.

Every transport implements `LiveCursorTransport`. Only `send` and `subscribe` are required. See [Transports](/docs/core/transports) for the full interface.

## Shared guard helpers

The Bun, Node.js (ws), Hono, Elysia, and Socket.IO relays share one file of guard helpers:

- room name validation (`parseRoom`)
- a token bucket rate limiter per connection (`RateLimiter`)
- a message size check (`messageByteLength`)
- origin and room token checks
- connection caps per room and per process (`ConnectionLimits`)
- identity binding (`bindIdentity`)

## Identity binding

A relay that does not decode messages cannot tell who sent a message. With identity binding, the `authCheck` hook returns a verified `{ clientId, user }`. The relay then writes that identity into every JSON frame of the connection. [Relay contract](/docs/examples/backends/relay-contract#identity) gives the rules and lists the relays that support it.

The entry files of the Bun, Node.js (ws), Hono and Elysia relays have a demo identity mode. To turn it on, set `RELAY_DEMO_IDENTITY=1` before you start the relay:

```sh
RELAY_DEMO_IDENTITY=1 bun relay.ts
```

In this mode, the [room token](/docs/dom/websocket-transport#room-token) names the user. `authCheck` returns `{ clientId: "user-<token>", user: { name: "<token>" } }`. A client with the room token `ada` gets the `clientId` `user-ada~<connection>` and the user `{ name: "ada" }`. The relay refuses a connection without a room token.

<Callout type="warn">
  If you use the demo identity mode in production, any client can claim any name. The relay trusts the room
  token as the user name. Check the room token in your own `authCheck`, for example as a JWT, and return the
  verified user.
</Callout>

## Conformance suite

`examples/_shared/relay-conformance-suite.ts` is a vitest suite that checks a relay against the relay contract. The Bun, Node.js (ws), Hono and Elysia relays pass the full suite. The suite connects with plain WebSockets. The Socket.IO relay and the SignalR hub speak their own protocol, so the suite does not run against them. See [Check your relay](/docs/examples/backends/relay-contract#check-your-relay) to run the suite against your own relay.
